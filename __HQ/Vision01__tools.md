## Принцип документации инструментов

```text
TOOLS.md
    ↓
ЧТО существует и для чего
    ↓
tool__TLDR.md
    ↓
КОГДА и КАКОЙ РЕЖИМ выбрать
    ↓
tool --help
    ↓
КАКИМ ТОЧНО интерфейсом пользоваться
    ↓
tool <arguments>
    ↓
ТОЛЬКО РЕЗУЛЬТАТ
```


## Main documentation rule:
Максимум понимание за минимум использованных токенов.  Все рассуждение и большие описания не нужны.  Каждое предложение должно быть оценено с точки зрения - можно ли его уменьшить оставив тотже смысл, если да - уменьшить.
### 1. `TOOLS.md` — каталог

**Назначение:** быстро понять, какие инструменты вообще существуют.

Для каждого tool — **одна строка**:

```text
codebase_import_search — finds where symbols from a target module are used across the project.
```

Никаких флагов, примеров, подробностей и описания режимов.

Дополнительно в самом `TOOLS.md` один раз можно сказать:

```text
Each tool has a corresponding <tool>__TLDR.md with usage guidance and exposes its complete CLI interface through --help.
```

То есть `TOOLS.md` отвечает только на:

> **«Какой инструмент мне нужен?»**

---

### 2. `<tool>__TLDR.md` — инструкция выбора

Это **не справочник параметров**.

Он отвечает на:

> **«Я нашёл инструмент. Как мне его применить для моей задачи?»**

Здесь должны быть:

1. **Одно предложение о назначении**, чтобы подтвердить, что tool подходит.
2. **Минимальное условие запуска** — например, `--file` или `--module`.
3. **Режимы**, сформулированные через задачу пользователя/агента:

   * что хочу узнать → default;
   * хочу upstream → `--incoming`;
   * нужны точные строки → `--verbose`;
   * нужна информация о тестах → `--tests-only`.
4. Только те дополнительные параметры, которые **реально влияют на выбор или понимание использования**.
5. Конфигурационные особенности, если без них легко получить неправильный результат.

Не надо дублировать:

* описание `--verbose` в Modes и потом ещё раз в таблице;
* описание `--incoming` дважды;
* полный `argparse`;
* все возможные значения параметров, если они уже очевидны или доступны через `--help`.

То есть TLDR отвечает:

> **«Какой способ вызова мне нужен?»**

---

### 3. `<tool>  --help` — полный CLI-контракт

Это уже **машиночитаемая/точная техническая документация интерфейса**.

Здесь:

* полный `usage`;
* все параметры;
* допустимые значения;
* defaults;
* ограничения;
* форматы аргументов;
* точное поведение каждого флага;
* всё, что необходимо знать для корректного вызова.

`--help` **не должен быть нужен для обычного использования**, если TLDR уже позволяет агенту выбрать правильный режим.

Он нужен когда:

> **«Мне нужна точная информация об интерфейсе, которой нет в TLDR.»**

---

### 4. Запуск без аргументов

Это отдельный важный уровень.

**Не показывать полный `--help`.**

Дать:

```text
codebase_import_search.py
Find where symbols from a target module are imported or used across the project.
Usage: codebase_import_search.py --file PATH [--module-names N1,N2,...] [--incoming|--verbose] [options]
Current PROJECT_ROOT="path to root"

Full help with --help
```

То есть:

> **WHAT + HOW TO START**

Без документации и без результатов.

Это особенно полезно, если агент случайно вызывает tool без аргументов: он получает достаточно информации, чтобы понять следующий шаг, но не получает 30 строк шума.

---

### 5. Обычный рабочий вызов

После того как аргументы переданы:

```text
tool <arguments>
```

выводится **только результат**.

Не надо:

```text
Running codebase_import_search...
Mode: default
Target: ...
Options:
...
```

если это не требуется самому результату.

То есть:

> **INPUT → RESULT**

---

## Универсальное правило раскрытия информации

Я бы сформулировал его так:

> **Раскрывай ровно тот уровень информации, который нужен для следующего действия, и не повторяй информацию, доступную на более глубоком уровне.**

Или ещё короче как правило для всей системы:

```text
Catalog → Purpose
TLDR    → Decision
Help    → Contract
Run     → Result
```

Где:

| Уровень       | Отвечает на вопрос       | Объём            |
| ------------- | ------------------------ | ---------------- |
| `TOOLS.md`    | **Что у меня есть?**     | минимум          |
| `*__TLDR.md`  | **Что выбрать и когда?** | кратко           |
| `--help`      | **Как точно вызвать?**   | полно            |
| рабочий вызов | **Что получилось?**      | только результат |

И важное следствие:

**Информация должна раскрываться по требованию, а не дублироваться на каждом уровне.**

Например, `--verbose` должен быть **объяснён в TLDR как выбор режима**, но его полная синтаксика и ограничения находятся в `--help`. В таблице TLDR второй раз его описывать уже не нужно.
