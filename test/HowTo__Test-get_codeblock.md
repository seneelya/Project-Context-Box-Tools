# HowTo: тестирование get_codeblock

Живёт здесь, в `__HQ/tools/test/`, рядом с самими тестами — не в docs-репо (`__dev/tools/`),
где эта копия раньше устарела и разошлась с реальностью (например: "outline для TS/C# пока не
реализован" — уже реализован; ноль слов про batch `--line` массивы). Актуальность = рядом с кодом.
Этот файл описывает подход СЕГОДНЯ и будет меняться по мере работы — не константа.

## Регресс — гонять ПЕРЕД коммитом, не после каждой правки

```bash
py test/check.py --fails          # оракул: 106 хендкрафченных кейсов (level/outline/query), 3 строки вывода
py test/sweep_invariants.py       # фаззер: каждая непустая строка каждого файла в test/, инварианты (CONTAIN/RANGE/CRASH/LEVEL)
```

- `check.py --fails` — дёшево (~3 строки), но это НЕ повод гонять его после каждой мелкой правки —
  копится в контексте без пользы. Гонять перед коммитом, когда правка реально готова.
- `sweep_invariants.py` — тоже перед коммитом. `--check-query` (медленнее, ~2x) — если правка
  трогает `resolve()`/адресацию, не только ladder. Подробности режимов — `test/README.md`.
- Оракул = `test/expected.py`, правится руками при находке реальной ошибки (не подгоняется под
  текущий баг). Sweep = структурные инварианты, не конкретные числа.

## Ручная проверка вывода — не гонять самой, просить проверить пользователя

Раньше агент прогонял вручную десятки вызовов `gcb` за сессию, разглядывая вывод сам — забивает
контекст без необходимости, если человек и так рядом и может глянуть быстрее. Текущий порядок:
1. Внести правку.
2. Прогнать РОВНО ОДИН показательный вызов (не батарею вариаций) — если нужно доказать себе, что
   код не упал, а не для дизайна формата.
3. Дизайн/формат вывода — показать команду и попросить пользователя прогнать и прислать вывод
   (она рядом, у неё дистиллят дешевле, чем у агента гонять и читать самому).

## Golden-тест реального вывода — `test/golden_check.py`

Регресс/sweep выше проверяют РУЧНЫЕ структурные факты (уровень такой-то строки, диапазон такой-то) —
не точный отрендеренный текст. `golden_check.py` — другое: реально запускает `gcb` (subprocess, не
импорт) на калибровочных файлах из `test/` и сравнивает stdout байт-в-байт с сохранённым файлом в
`test/golden/`. Ловит именно то, что этот файл разбирал всю сессию — разъезд колонок, забытый
маркер, случайно изменившийся текст — то, что оракул структурных фактов не увидит вообще.

```bash
py test/golden_check.py                    # сверить все кейсы
py test/golden_check.py NAME               # сверить один именованный кейс
py test/golden_check.py --record           # перезаписать ВСЕ эталоны текущим выводом
py test/golden_check.py --record NAME      # перезаписать один
```

При несовпадении — сигнал + количество несовпавших строк + их номера (не полный diff-дамп).
`--record` — это заявление "этот вывод сейчас ПРАВИЛЬНЫЙ", а не просто "вот что получилось" —
перед коммитом `--record`-а надо реально посмотреть на новый файл в `test/golden/`, не штамповать
не глядя. Список кейсов и фикстур — прямо в начале `golden_check.py` (`CASES`).

## Что уже умеет `gcb` (см. `--help` и `CONTRACT.md` — источник истины по формату)

- `--outline` — работает для Python/TS/C#/Markdown (НЕ "пока не реализован" — это устарело).
- `--line N` — **массив**: `--line 1827,606,867`, один файл-парс. `--level`/`--ancestor-level`
  тоже массивом, broadcast-правило см. `get_codeblock/reader/CONTRACT.md`.
- Три verb-режима батча: survey (голая лестница, ОДНА объединённая карта на весь батч, не N
  отдельных), `--outline --line …` (то же самое дерево, другой источник строк), `--query --line …`
  (тела блоков, merge касающихся/вложенных диапазонов, ошибка одного хита не роняет остальные).
- `--dot` — тот же рендер что `--outline`, но filler показан на ВСЕХ уровнях (диагностика — что
  реально увидит grep).
