# Plan04 — split_monster: генератор исполняемого скрипта-переноса вместо JSON/YAML-спеки

Основа: `Vision06__monster-file-split.md` (все решения и рационале — там, особенно секция
«Интерфейс v0/v1» от 2026-09-16 и её продолжение в тот же день; здесь — порядок реализации v0).
Прикладная цель: разрезка `core.js`/`file-ops-pane.js`/`operation-card.js` в hermes-filetools по
`Plan21__panel-decomposition.md`.

Это ЗАМЕНА более ранней редакции этого плана (JSON/YAML `--spec`-контракт, затем «пишу весь скрипт
руками») — обе отклонены живым обсуждением, см. Vision06. Финальная форма: от меня — минимальный
вход прямо в CLI (номер строки → целевой файл, без промежуточного файла); `split_monster` это
разворачивает в готовый трёхслойный Python-скрипт + дешёвые эвристические подсказки в комментариях;
я его читаю, точечно правлю (дописывая строки снизу, не редактируя существующие) и запускаю.

## Пункт 0 — форма поставки

`__HQ/tools/split_monster.py` — одновременно CLI (`--generate`, см. Пункт 2) и библиотека примитивов
(Пункт 1), которую импортирует сгенерированный скрипт. Единственный вход в тул с моей стороны —
`split_monster --file ... --split ... --out-script ...`, дальше `python <скрипт>.py`.

Безопасность («сначала посмотреть») — не `--dry-run`-флаг тула, а сам `--apply` как аргумент ЗАПУСКА
сгенерированного скрипта: `python my_move.py` без флага — печатает план (что откуда куда, без
записи), `python my_move.py --apply` — пишет на диск. Проверяется одной строкой
(`'--apply' in sys.argv`) внутри `monster.write`/`monster.cut`, без argparse внутри самого
сгенерированного скрипта — это забота библиотеки, не мой ручной код.

## Пункт 1 — примитивы библиотеки (сигнатуры)

- `cut(source_file: str, line: int) -> Block` — резолвит СРАЗУ (не лениво): вызывает
  `get_codeblock(source_file, line, level=1, query=True)` (импорт из `get_codeblock.core`,
  см. Vision06), возвращает лёгкий объект/dict `{source_file, start, end, text}`. Явный
  `source_file` на каждый вызов — без скрытого «текущего файла по умолчанию»: дороже на пару
  символов, зато ноль неявного состояния (тот же принцип, что у самого `get_codeblock()` —
  `file_path` всегда явный аргумент).
- `add_import(text: str) -> Import` — просто оборачивает строку в маркерный тип (ничего не
  резолвит; на v0 тул не угадывает импорты — если нужен, дописываю сама, правкой уже
  сгенерированного скрипта).
- `monster.write(target_file: str, blocks: list[Block], imports: list[Import])` — при вызове (не
  раньше): дедуп `imports` в шапку, `blocks` — в тело в ВОССТАНОВЛЕННОМ порядке (см. Пункт 3),
  запись (или печать плана без `--apply`).
- `monster.cut(source_file: str, blocks: list[Block])` — вырезает диапазоны `blocks`, чьи
  `.source_file == source_file`, из самого `source_file` (несовпадение — исключение, защита от
  случайно не того списка). Тоже пишет только под `--apply`.

Эти примитивы используются ОДИНАКОВО что в сгенерированном (Пункт 2), что в ручном скрипте — сама
библиотека не знает и не обязана знать, откуда взялся вызывающий её код.

## Пункт 2 — режим `--generate` (главный вход на v0)

CLI-форма (черновик, доводится при реализации):
```
split_monster --file desktop/src/core.js \
  --split 123 "desktop/src/core-format.js" \
  --split 456 "desktop/src/core-format.js" \
  --out-script my_move.py
```
`--split LINE TARGET` — повторяемый флаг (`nargs=2, action='append'`), НЕ один плоский список на
все пары — так не завязываемся на чётность общего числа аргументов. `LINE` — номер строки начала
объекта, тот же, что я вижу в `--outline` (вызываю сама, до этого шага). `--out-script` — куда
записать результат.

Генерация разворачивает пары в скрипт по формату Vision06 (три слоя: данные → действия → сборка,
`#N`-теги, ничего не смешивается на одной строке с кодом — см. Примеры А/Б там). Для КАЖДОГО
диапазона тул сам:
1. резолвит `{start, end, text}` через `get_codeblock` — end мне вводить не нужно, только start
2. вставляет сигнатуру/первую строку блока отдельным комментарием НАД кодовой строкой (то самое
   «видно, что реально вырезается», без повторного запроса с моей стороны)
3. дописывает ДЕШЁВУЮ эвристическую подсказку — простой текстовый скан (НЕ через tree-sitter,
   НЕ настоящий резолв): (а) грep имени блока по остальному файлу — кто ещё его упоминает,
   (б) какие идентификаторы тела блока совпадают с другими топ-левел именами файла. Помечается в
   комментарии явно как best-effort («затычка» v0, не источник истины — см. Vision06). Ложные
   срабатывания ожидаемы (не отличает переменную от одноимённого поля объекта) — я это верифицирую
   глазами, тул не подставляет импорты сам на основе этой подсказки

Группировка (`line → target_file`) — по-прежнему МОЯ работа (читаю файл, решаю), тул её не
предлагает — это разница между v0 и v1, не разница в том, генерируется ли скрипт (см. Vision06).

## Пункт 3 — порядок и восстановление последовательности

Раз `cut()` резолвит СРАЗУ на вызове (не откладывая), а генератор строит `BLOCKS01 = [c01, c02, ...]`
в том порядке, в котором Я передала пары `--split` — специально восстанавливать порядок на этом
уровне нечего, если только я сама передала пары в порядке появления в источнике (обычный случай).
Восстановление нужно внутри `monster.write`, когда блоки из НЕСКОЛЬКИХ источников или повторного
запуска (дозапись в уже существующий `target_file`) должны лечь в правильную относительную
последовательность — приём из Vision06: сортировка по `start` по убыванию + вставка каждого блока в
НАЧАЛО уже накопленного тела (а не апенд), что восстанавливает исходный порядок автоматически.
Диапазоны вырезаются из `source_file` (в `monster.cut`) тоже строго по убыванию `start` — более
ранние номера строк не должны уехать раньше, чем их прочитали.

## Пункт 4 — потребители (`consumers_of`)

`--generate` (или отдельно) может дописать в скрипт вызов `monster.consumers("desktop/src/core.js",
[...])` — тонкая обёртка над `make_interface_card.consumers_of`, печатает (не пишет) список
`{symbol: [(consumer, line), ...]}` для сверки. Обязательно ДО первой мутации `source_file` —
`consumers_of` парсит живые декларации, после вырезки символа там для неё уже ничего нет (см.
Vision06). Внешние импорты потребителей тул не чинит — только показывает, правка руками.

## Пункт 5 — тесты (маленькие фикстуры, не hermes-filetools)

- `--generate` на фикстуре с известными строками → сгенерированный скрипт содержит ожидаемые
  `cut(...)`/`#N`-теги/слои в правильном формате (сравнение с ожидаемым текстом скрипта)
- эвристическая подсказка — на фикстуре с заведомо известными «кто ссылается» — просто проверка,
  что скан находит очевидные случаи (не полнота, только что механизм не сломан)
- `cut()` — байт-в-байт совпадение с содержимым фикстуры на известном диапазоне
- `monster.write` — два блока в один `target_file`, порядок в результате совпадает с порядком
  в источнике
- повторный `monster.write` в уже существующий `target_file` — новые блоки встают ПЕРЕД старым
  телом, импорты дописываются в шапку без дублей
- без `--apply` (аргумент не передан) — ни один файл не создаётся и не меняется, план печатается
- `monster.cut` — вырезает ровно те диапазоны, чей `source_file` совпадает; несовпадение — исключение

## Пункт 6 — порядок работы

1. `cut()`/`add_import()` + `monster.write`/`monster.cut` (Пункты 1, 3) без `--apply`-ветки записи,
   юнит-тесты на фикстурах.
2. Добавить фактическую запись за `--apply`, тесты на временную директорию.
3. `--generate` (Пункт 2) — сначала без эвристической подсказки (голый скелет: данные/действия/
   сборка/теги), затем добавить грep-эвристику отдельным шагом.
4. `monster.consumers(...)` (Пункт 4).
5. Обкатать на ОДНОМ маленьком переносе из `Plan21` (`formatDuration` → `core-format.js`) —
   сгенерировать скрипт, прогнать без `--apply` (сверить план глазами), затем с `--apply`, прогнать
   регрессию hermes-filetools (`pytest`/`node --test`/`check_seams.py`), только после этого — весь
   остальной перенос по `core.js`, затем `file-ops-pane.js`/`operation-card.js` по риск-порядку из
   `Plan21`.
