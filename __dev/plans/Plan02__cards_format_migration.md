# Plan02 — cards format migration (merge-friendly facts + card-version marker)

## Зачем

Три места в карточке склеивают несколько значений в одну физическую строку через
запятую — если несколько человек параллельно добавляют что-то новое (потребителя,
подмодуль, импортируемый символ), они правят ОДНУ И ТУ ЖЕ строку на разных ветках,
и это гарантированный git-конфликт при мердже, даже когда по смыслу конфликта нет
(оба просто ЧТО-ТО добавили). Плюс отдельная находка: `Why` в таблице
`Dependencies Internal` смешивает машинный факт и прозу человека в одной строке —
LLM, дописывая своё пояснение, вынуждена переписывать всю строку целиком (включая
факты), и правка прозы конфликтует с ростом списка символов по той же причине.

Общий приём: там, где раньше было «N значений в одной строке», делаем «одно
значение — одна строка» (bullet-список / отдельная строка таблицы). Тогда два
независимых добавления — это две РАЗНЫЕ строки, а не два разных редактирования
одной и той же — мердж сходится сам почти всегда, а когда не сходится, разрешается
тривиально (оставить обе добавленные строки, не пересобирать текст руками).

## Пункт 0 — версия формата, впечатанная в саму карточку

Версия контракта сама по себе (константа в `CARD_FORMAT.py`) бесполезна, если
УЖЕ ПРОШТАМПОВАННЫЕ карточки не несут в себе, каким форматом их писали. Нужна
версия именно В КАЖДОМ ФАЙЛЕ.

- `CARD_FORMAT.py`: добавить `VERSION = "1.0.0"` — источник истины, какой формат
  тул сейчас умеет писать. Бампается при любой правке, меняющей ON-DISK формат
  карточки (имена секций, колонки таблиц, список-vs-одна-строка, маркер директивы)
  — по аналогии с `get_codeblock/core.py`'s `VERSION`.
- `make_interface_card.py`: при штампе дописывает **последней строкой файла**
  `<!-- card-format: 1.0.0 -->` — HTML-комментарий, невидим в markdown-превью,
  тривиально грепается, и сразу понятен человеку/LLM, открывшему файл: «а, вот
  какой версией это писали».
- Почему последней строкой, а не сразу после H1: чтобы не путаться с summary/
  прозой секций и не разбираться, где именно она может «утечь» в парсинг —
  вместо точечных скипов в каждом месте разбора делаем ОДИН общий шаг в начале
  `_parse_old_prose`: до всякого разбора на секции — вычистить из `lines` любую
  строку, совпавшую с паттерном `<!-- card-format: … -->`, откуда бы она ни
  взялась. После этого фильтра положение строки в файле — вопрос читаемости,
  не корректности парсинга.
- Старые (уже существующие) карточки версии не несут вообще — это нормально,
  различаем их структурно (см. пункт 3), не по версии. Ценность версии — на
  будущее: следующий переход формата будет определяться чтением этой строки,
  а не структурным гаданием заново.

## Файлы, которые трогаем

- `make_interface_card.py` — вся суть (рендер + парсинг).
- `CARD_FORMAT.py` — контракт формата (доки, `EDGE_COLUMN`, каноничные имена секций, `VERSION`).
- `test/test_cardstamp.py`, `test/expected.py` — фикстуры, ссылающиеся на старый формат.
- `graph_from_cards.py`, `validate_cards.py` — НЕ трогаем логику (уже проверено: они не читают `Why`, а `File Path` как колонка остаётся на месте) — прогоняем как регрессию, не как правку.

## Порядок реализации (каждый пункт — независимый, можно коммитить по отдельности)

**1. Consumers → bullet-список**
- `_consumers_fact` → рендерит `consumers N:` + `- file` построчно вместо одной строки.
- `_parse_entries` (сейчас строка ~409): текущий скип `not ln.strip().startswith("consumers ")` — это ОДНА строка; расширить до блока: после строки `consumers N:` скипать все идущие подряд `- `-строки.
- Ничего не парсится «взад» в `P` — это чистый факт, миграция не нужна, следующий штамп просто рисует по-новому.

**2. Package layout submodules → bullet-список**
- Рендер (сейчас строка ~604): `known submodules (re-exported from):` + список одной строкой → шапка + `- modname` построчно.
- `_parse_old_prose`, ветка `Package layout`: фильтр `not ln.strip().startswith("known submodules...")` — расширить с одной строки до блока тем же приёмом.

**3. Dependencies Internal — таблица без Why + строка-на-символ + отдельный Why-блок**
- Рендер таблицы: убрать колонку `Why`, оставить `Import | File Path | Symbols | Kind`; один `r` в `resolved` даёт список символов на файл — разворачиваем в N строк (по символу), а не одну строку с join.
- После таблицы — новая H3-подсекция внутри того же H2 (`## Dependencies Internal`), с поясняющим заголовком, а не голым словом:

  ```
  ## Dependencies Internal

  | Import | File Path | Symbols | Kind |
  |---|---|---|---|
  | `utils` | `utils.py` | `bar` | normal |
  | `utils` | `utils.py` | `baz` | normal |
  | `config` | `config.py` | `SETTINGS` | normal |

  ### Why these imports are used (one line per import — free text)
  - `utils` — <прозу пишет агент>
  - `config` — <прозу пишет агент>
  ```

  Bullet — по уникальному `import`-ключу (дедуп после разбиения таблицы на
  строку-на-символ), с директивой `DIRECTIVE_WHY` для ключей без сохранённой
  прозы. H3 внутри того же H2 — по аналогии с тем, как `Public API` уже
  вкладывает H3-подсекции: `Why` остаётся концептуально частью `Dependencies
  Internal`, не отдельным несвязанным H2.
- Парсинг (авто-миграция прозы, без ручного переноса):
  - `_parse_why` (старый, табличный, по имени колонки `Why`) — ОСТАВИТЬ как есть — это мост для одноразового чтения ещё не мигрированных карточек.
  - Новая функция (условно `_parse_why_section`) — читает bullet-список из новой H3-подсекции, пишет в тот же `P["why"]`.
  - `_parse_old_prose`, ветка `Dependencies Internal`: тело секции сначала режем по маркеру `### Why...` — то, что до него, в `_parse_why` (легаси-путь), то, что после — в новый парсер. Обе функции пишут в один и тот же словарь; конфликта не будет (карточка либо ещё табличная, либо уже мигрированная, не оба сразу).
  - Рендер всегда пишет ТОЛЬКО новый формат — откуда бы прозa ни была прочитана.
