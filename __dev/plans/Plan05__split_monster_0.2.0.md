## Находка 1 — пропавшие рантайм-импорты (react/jsx-runtime, хуки, соседние файлы типа brick.js)

**Что было руками:** три раза подряд (core-format/window, три operation-card-файла) — грепом искать
usage хуков/внешних примитивов по диапазону и писать шапку импортов с нуля в каждый новый файл.

**Источник данных — уже готовый, чужой, не писать заново.**
`find_code_usage.handlers.ts_handler.TypeScriptHandler` уже держит скомпилированные регексы на все
формы импорта (`ES_NAMED_RE`/`ES_DEFAULT_RE`/`ES_NAMESPACE_RE`/`CJS_REQUIRE_RE`/
`CJS_DESTRUCTURE_RE`/`DYNAMIC_NAMESPACE_RE`/`DYNAMIC_DESTRUCTURE_RE`) — те же самые, что чинили
сегодня (Plan04-CARRY п.4). `split_monster` их ИМПОРТИРУЕТ (не копирует, не переизобретает),
прогоняет по ПЕРВЫМ строкам `source_file` (до первой не-import/не-comment строки) и строит
`{specifier: [name, ...]}` — не резолвя ничего, просто читая, что сам файл объявляет импортом.

**Механика:**
1. Новая функция `_source_imports(source_lines) -> list[{specifier, names}]` в `split_monster.py` —
   гоняет регексы `ts_handler`'а по ведущим строкам файла (тот же цикл, что в `analyze_file`, но БЕЗ
   `matches_target` — здесь не с кем сравнивать, нужны ВСЕ имена, не только совпавшие с целью).
2. Для каждого `cut()`-блока — тот же `_WORD_RE.findall(block.text)`, что уже даёт внутреннюю
   best-effort подсказку (Vision06, находка есть в v0), только теперь СВЕРКА идёт ещё и против
   объединения всех `names` из `_source_imports()`.
3. На каждый `target_file` — объединение (union) найденных имён по каждому `specifier` СО ВСЕХ его
   блоков, и уже готовый `add_import(...)` в сгенерированный скрипт (не просто комментарий-подсказка,
   как для внутренних best-effort — здесь источник (список импортов самого файла) точный, не
   догадка). Формат строки: `import { <names> } from '<specifier>'` — реконструируется, не
   копируется дословно (в одном таргете может понадобиться подмножество имён одного специфаера).
4. Как и любой `add_import` — это ПРЕДЛОЖЕНИЕ, готовое к запуску, но я его вижу и могу убрать/
   поправить той же техникой (дописать строку снизу), что и раньше. Ложные срабатывания того же
   рода, что и у существующей best-effort подсказки (комментарий, а не код) — не исключены,
   не смертельны.

**Тесты:** фикстура с `import { jsx } from 'react/jsx-runtime'` + `import { useState } from 'react'`
наверху, блок использующий оба — сгенерированный скрипт содержит `add_import` на каждый специфаер с
верно объединённым списком имён; блок, не использующий специфаер вовсе — этот `add_import` не
появляется в его группе.

## Находка 2 — осиротевшие комментарии-рационале (get_codeblock уже видит их сам)

**Что было руками:** шесть отдельных Edit-пар (снять/вставить) на `operation-card.js` — комментарии,
не слившиеся с функцией из-за пустой строки-разделителя, оставались сиротами в файле-источнике.

**Источник данных — уже готовый, чужая функция, не новый анализ.**
`get_codeblock/reader/classify.py::outline_rows(path, deep=False)` — та же функция, что рендерит
`--outline`. Возвращает ПЛОСКИЙ список `{level, start, end, text, frame, filler}` на ВЕСЬ файл разом.
`filler=True` (или `text` вида `~kind`, если `b.name` пуст) — анонимная запись: голый комментарий,
expression-statement и т.п., НЕ слившаяся с named-блоком по имени. Это ровно те `.`-записи, что видны
в CLI-рендере `--outline` — сурфейсить, не считать заново.

**Механика:**
1. `generate()` вызывает `outline_rows(file_path)` ОДИН раз на весь батч (не на каждый `cut()`).
2. Для каждого `--split`-диапазона (уже резолвнутого через `cut()` в `{start, end}`) — ищем
   ближайшую строку `outline_rows` СТРОГО ПЕРЕД `start`, у которой `filler=True` (или анонимный
   `text`) и чей `end` НЕ входит в уже резолвнутый `[start, end]` (то есть она НЕ была частью того
   же banded-диапазона, который уже слился в блок — иначе дублируем то, что уже видно в `_preview_line`).
3. Если нашли — печатаем в сгенерированный скрипт короткую строку-памятку НАД `cut(...)`:
   `# ПАМЯТКА: возможно относящийся комментарий — строки [X-Y] в источнике, не перенесён автоматически`
   Только номера строк, не сам текст (текст может быть длинным, это отдельная забота при
   реализации Находки 2 — списка, "заполненного, но не добавленного", как просила владелец).
4. Ничего не переносится автоматически. Решение (перенести/оставить/разбить) — моё, как и раньше.

**Тесты:** фикстура — комментарий с пустой строкой перед функцией, `--split` на эту функцию →
сгенерированный скрипт содержит памятку с верным диапазоном строк комментария. Комментарий БЕЗ
пустой строки (уже часть банды) → памятки нет (уже покрыто существующим `_preview_line`).
