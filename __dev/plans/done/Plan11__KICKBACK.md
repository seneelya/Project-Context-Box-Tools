## K1 — major: сырые диапазоны baseline не равны публичным диапазонам --name

**Адрес:** шаг 4, строки 113–116; «Готово», строка 151.

Формулировки «348 функций, диапазоны совпадают с baseline» и «--name каждой
функции находит ровно её диапазон» допускают требование побайтного совпадения
публичного блока с сырым function_definition. Это противоречит действующим
правилам get_codeblock:

- Начало публичного блока включает приклеенную преамбулу комментариев
  (`reader/CONTRACT.md:375`, инвариант #6). В baseline комментариев перед функцией
  нет: например, функция с комментарием-преамбулой в cover-map.fs: сырой диапазон 42–47, комментарий
  на строке 41. Публичная карта/адресация вправе начинать этот блок с 41.
- CLI auto-escalation расширяет маленькие блоки, если не передать `--force`
  (`get_codeblock__TLDR.md:102`). В наборе есть однострочные функции.
- `--name` маршрутизируется в существующий `--line` render, не задаёт новый
  независимый способ нарезки. Ради нового языка не нужно менять эти правила.

**Предлагаемая формулировка приёмки:**

1. Отдельно сверить все 348 сырых function_definition: имя/сигнатуру и исходный
   диапазон — с baseline (как в Plan10).
2. `--name NAME --force` должен разрешить нужную функцию и выдать тот же публичный
   диапазон и текст, что `--line <строка сигнатуры> --query --force`. Публичный
   диапазон определяется CONTRACT, включая преамбулу; сверять его с картой.
3. Обычный `--name` без --force сохраняет действующую эскалацию; отдельно проверить,
   что диагностическая шапка честно сообщает расширение.

В текущих 22 файлах одинаковых имён функций внутри одного файла по baseline не
обнаружено. Общий контракт неоднозначных имён/перегрузок при этом не переопределять.

## K2 — major: ссылка на wheel сама по себе не обеспечивает корректную установку и отказ

**Адрес:** D7/D8, шаг 2 (`env_check`, `requirements.txt`), шаг 4 (проверка без wheel).

Проверено существующее поведение `get_codeblock/env_check.py`:

- `parse_requirements` (49–75) умеет отделять имя пакета от version spec, но НЕ
  выделяет import-модуль из wheel-пути/direct reference и не обрабатывает markers;
- `ensure_language` (103–115) проверяет только `find_spec`, а при отсутствии
  сопоставления в requirements подставляет `tree-sitter-glsl-spec` как имя PyPI-пакета;
- `install_command` (82–86) просто соединяет имена в `pip install ...`.

Если лишь добавить модуль в LANGUAGE_MODULES и путь wheel в requirements,
сообщение об отсутствующей GLSL-зависимости может предложить установить
**сломанный upstream 1.0.0 из PyPI**. Если этот upstream уже установлен,
`find_spec` сочтёт зависимость наличной, и ранее доказанный OverflowError остаётся
возможен при загрузке языка. Это реальные конфигурации, не гипотетические риски.

Отдельно: безусловная ссылка на `win_amd64.whl` в общем requirements сломает
установку остальных языков на Linux/macOS и неподходящих архитектурах. Относительный
путь к wheel нужно согласовать с cwd: файл лежит в tools/wheels, а requirements —
в tools/get_codeblock. D8 о поставке wheel файлом не оспаривается.

**Предлагаемое уточнение объёма/приёмки:**

1. Предусмотреть общий, заданный данными способ сопоставить import-модуль с локальным
   артефактом/командой установки (либо поддержать нужный синтаксис requirements).
   Не добавлять частный `if language == 'glsl'` в общий механизм.
2. При отсутствии wheel сообщение ведёт именно к поставляемому capsule1 и даёт
   корректную команду для текущего Python/доступного пути, а не к PyPI 1.0.0.
3. При установленном старом upstream 1.0.0 — тоже чистый отказ с исправлением,
   БЕЗ ctypes-моста и без traceback. Способ проверки (метаданные/тип language result)
   оставить реализационным выбором; старую грамматику тестировать изолированно.
4. Windows wheel не становится обязательной непригодной зависимостью для других
   платформ/архитектур. Зафиксировать поддерживаемый cwd команды установки или
   разрешать путь от расположения requirements; проверить подсказку из другого cwd.
   Для неподдерживаемой платформы — честно сообщить ограничение поставленного wheel,
   не предлагать заведомо непригодную команду.

Это не требует Linux/macOS-сборок и не расширяет план на Hermes. Требуется сохранить
работоспособность общего механизма зависимостей и довести D7/D8 до проверяемого поведения.
