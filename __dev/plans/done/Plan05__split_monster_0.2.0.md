## Общая правка, общая для обеих находок — источник имён и уровней

**Заменяем regex-эвристику `_TOP_LEVEL_NAME_RE`/`_all_top_level_names` на `outline_rows`** (тот же
движок, что рендерит `--outline`) как источник истины для имён и уровней — не переизобретаем свой
парсер там, где уже есть настоящий (tree-sitter-based) классификатор.

**`Block` получает поле `.level`** (сейчас `get_codeblock`'s `res["level"]` есть, но отбрасывается) —
нужно, чтобы поиск имён/сирот всегда сверялся на ТОМ ЖЕ уровне, что и резолвнутый блок, а не считал
файл плоской лентой. Сегодня `cut()` всегда резолвит `level=1`, но `outline_rows` в принципе видит и
вложенные уровни (метод внутри класса и т.п.) — если `--split` когда-нибудь научится адресовать не
только верхний уровень, эта развязка не потребует переписывания.

**Банд (диапазон, слившийся из 2-3 объявлений без пустой строки между ними) — показываем как
отдельные ИМЕНОВАННЫЕ записи, каждая со своим именем**, не одной строкой "name1, name2" — чтобы при
необходимости было видно, что внутри одного `cut()`-диапазона едет несколько объектов, и это было
разборчиво человеку/будущей сессии (механически всё равно разделить их через `cut()` нельзя — оба
имени резолвятся в один и тот же диапазон, это просто видимость состава, не операция).

**`monster.consumers()` должен получать ВСЕ имена банда**, а не первое (`_block_name()` сегодня берёт
только первое совпадение регекса — значит внешние потребители второго объекта банда сейчас вообще не
проверяются; реальный, пусть и мелкий, баг v0, попутно чинится).

## Находка 1 — пропавшие рантайм-импорты (react/jsx-runtime, хуки, соседние файлы типа brick.js)

**Что было руками:** три раза подряд (core-format/window, три operation-card-файла) — грепом искать
usage хуков/внешних примитивов по диапазону и писать шапку импортов с нуля в каждый новый файл.

**Источник данных — уже готовый, чужой, не писать заново.**
`find_code_usage.handlers.ts_handler.TypeScriptHandler` уже держит скомпилированные регексы на все
формы импорта (`ES_NAMED_RE`/`ES_DEFAULT_RE`/`ES_NAMESPACE_RE`/`CJS_REQUIRE_RE`/
`CJS_DESTRUCTURE_RE`/`DYNAMIC_NAMESPACE_RE`/`DYNAMIC_DESTRUCTURE_RE`) — те же самые, что чинили
сегодня (Plan04-CARRY п.4). `split_monster` их ИМПОРТИРУЕТ (не копирует, не переизобретает),
прогоняет по ведущим строкам `source_file` (до первой не-import/не-comment строки, через тот же
`_join_multiline_imports`, что и `analyze_file` — иначе многострочный `import {...}` в самом
`source_file` пропадёт тем же багом, что чинили сегодня для потребителей) и строит
`{specifier: [(name, kind), ...]}` — не резолвя ничего, просто читая, что сам файл объявляет
импортом. **Все три вида** (`ES_NAMED_RE`/`ES_DEFAULT_RE`/`ES_NAMESPACE_RE`), не только named —
`kind` нужен, потому что реконструкция строки разная (`import { a, b } from 'x'` vs
`import Foo from 'x'` vs `import * as ns from 'x'`), плоским списком имён не описать.

**Механика:**
1. Новая функция `_source_imports(source_lines) -> list[{specifier, kind, names}]` в
   `split_monster.py` — гоняет регексы `ts_handler`'а (все три ES-формы) по ведущим строкам файла
   (тот же цикл, что в `analyze_file`, но БЕЗ `matches_target` — здесь не с кем сравнивать, нужны ВСЕ
   имена, не только совпавшие с целью).
2. Для каждого `cut()`-блока — тот же `_WORD_RE.findall(block.text)`, что уже даёт внутреннюю
   best-effort подсказку (Vision06, находка есть в v0), только теперь СВЕРКА идёт ещё и против
   объединения всех `names` из `_source_imports()`.
3. На каждый `target_file` — объединение (union) найденных имён по каждому `specifier` СО ВСЕХ его
   блоков, и уже готовый `add_import(...)` в сгенерированный скрипт (не просто комментарий-подсказка,
   как для внутренних best-effort — здесь источник (список импортов самого файла) точный, не
   догадка). Формат строки зависит от `kind` специфаера (см. выше) — в одном таргете может
   понадобиться подмножество имён одного named-специфаера.
4. Как и любой `add_import` — это ПРЕДЛОЖЕНИЕ, готовое к запуску, но я его вижу и могу убрать/
   поправить той же техникой (дописать строку снизу), что и раньше. Ложные срабатывания того же
   рода, что и у существующей best-effort подсказки (комментарий, а не код) — не исключены,
   не смертельны.

**Тесты:** фикстура с `import { jsx } from 'react/jsx-runtime'` + `import { useState } from 'react'`
наверху, блок использующий оба — сгенерированный скрипт содержит `add_import` на каждый специфаер с
верно объединённым списком имён; блок, не использующий специфаер вовсе — этот `add_import` не
появляется в его группе. Плюс фикстура на default/namespace импорт источника — реконструкция верного
вида строки.

## Находка 2 — осиротевшие комментарии-рационале (get_codeblock уже видит их сам)

**Что было руками:** шесть отдельных Edit-пар (снять/вставить) на `operation-card.js` — комментарии,
не слившиеся с функцией из-за пустой строки-разделителя, оставались сиротами в файле-источнике.

**Источник данных — уже готовый, чужая функция, не новый анализ.**
`get_codeblock/reader/classify.py::outline_rows(path, deep=False)` — та же функция, что рендерит
`--outline`. Возвращает ПЛОСКИЙ список `{level, start, end, text, frame, filler}` на ВЕСЬ файл разом.
`filler=True` (или `text` вида `~kind`, если `b.name` пуст) — анонимная запись: голый комментарий,
expression-statement и т.п., НЕ слившаяся с named-блоком по имени. Это ровно те `.`-записи, что видны
в CLI-рендере `--outline` — сурфейсить, не считать заново.

**Механика (пересмотрено — не "ближайший сосед", а промежуток по уровню):**
1. `generate()` вызывает `outline_rows(file_path)` ОДИН раз на весь батч (не на каждый `cut()`).
2. Комментарии/импорты/константы обычно лежат РЯДОМ со своим потребителем — поэтому кандидатов ищем
   ТОЛЬКО в промежутках, ПРИМЫКАЮЩИХ к уже выбранным `--split`-целям (до и после), не по всему файлу
   (это была бы уже территория находки 3/графа).
3. Для каждого резолвнутого блока (своего `.level`, см. выше) — берём ВСЕ строки `outline_rows` того
   же уровня, идём от блока в обе стороны (вверх и вниз) до ближайшего именованного (non-filler)
   лендмарка этого уровня — это и есть промежуток. Все `filler=True`-записи в промежутке, чей диапазон
   НЕ входит в уже резолвнутый `[start, end]` самого блока (иначе дублируем то, что уже видно в
   `_preview_line` — банд уже унёс их автоматически), — кандидаты.
4. Блок на другом уровне (например, метод класса, если/когда `--split` научится адресовать не только
   уровень 1) не считается соседом — сравнение промежутков всегда внутри одного уровня, не поперёк
   ("разорванный диапазон" — цель на уровне 1 и цель на уровне 2 внутри одного батча не смежны друг
   другу, даже если их резолвнутые диапазоны физически пересекаются в файле).
5. Каждый кандидат печатается в сгенерированный скрипт как ОТДЕЛЬНАЯ закомментированная строка-
   приглашение (не включена в перенос):
   `# кандидат (не включён): строки [X-Y], уровень N, до/после <цель> — допиши: cNN = cut(FILE, X)`
   Только номера строк, не сам текст (текст может быть длинным — не тащить в скрипт).
6. Ничего не переносится автоматически. Решение (перенести/оставить/разбить) — моё, как и раньше —
   через тот же приём "допиши строку снизу", что и везде в этом тулe.

**Приглашение шире, чем просто выбор из кандидатов** — в шапку сгенерированного скрипта добавляется
явный коммент: список кандидатов НЕ единственный способ забрать что-то ещё. Раз тул работает без
графа, он в принципе может не увидеть и не предложить как кандидата что-то нужное, лежащее не рядом
(например константу "из другого конца файла") — в этом случае ничего не мешает вызвать `cut(FILE,
LINE)` на ЛЮБУЮ строку вручную (через `get_codeblock --outline`, чтобы найти нужный диапазон) и
дописать её в скрипт той же техникой (`cNN = cut(...)`, добавить в `_BLOCKS`-список) — без перезапуска
`generate()`.

**Тесты:** фикстура — комментарий с пустой строкой перед функцией, `--split` на эту функцию →
сгенерированный скрипт содержит кандидата с верным диапазоном строк комментария. Комментарий БЕЗ
пустой строки (уже часть банды) → кандидата нет (уже покрыто существующим `_preview_line`). Фикстура
с комментарием ПОСЛЕ цели (не только до) → тоже кандидат. Фикстура с целями на разных уровнях в одном
батче → кандидаты каждого уровня ищутся независимо, не переходят на чужой уровень.

## CARRY — что унести в v1 (граф блок↔блок)

1. **Тул не видит "символ теперь пересекает границу файла → нужен export".** На
   `file-ops-pane.js` два перенесённых символа (`DropStrip`, `FilterBar`) были file-private в
   исходнике (никогда не экспортировались — использовались только внутри того же файла); после
   переезда в новый файл им нужен `export`, иначе импорт в оставшемся файле не сработает. Тул
   этого не предлагает и предложить не может без резолва фактических потребителей ПОСЛЕ
   переноса — ровно то, для чего нужен настоящий граф (v1), не грепом угадать. Мелкая, но
   систематическая ручная правка на каждой разрезке, где переносится file-private символ,
   всё ещё нужный в старом доме.
2. Находка 1/2 подтвердили себя на ВТОРОМ реальном файле подряд (после core.js/
   operation-card.js в предыдущей сессии) — ни одной ручной подгонки импортов, ни одного
   пропущенного сироты-комментария. v0.2.0 можно считать закрытым, новых дешёвых находок в
   этом прогоне не всплыло — то, что остаётся (export-пробел выше), уже требует графа.
