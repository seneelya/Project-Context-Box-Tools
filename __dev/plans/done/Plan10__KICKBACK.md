## K1 — major: существующий probe не является проверкой успешности сборки

**Адрес:** Plan10, шаг 4.1–4.4, строки 94–101; «Готово», строки 127–129.
**Основание:** `__dev/review/glsl_probe.py`, блок 119–155.

Сейчас скрипт диагностический:

- падение worker записывает в `crashes`, но само по себе НЕ делает код выхода
  родителя ненулевым;
- `probe()` ловит неудачную прямую загрузку, затем использует ctypes-мост;
  то есть успешный разбор ещё не доказывает прямую загрузку исправленной обёртки;
- основной запуск всегда проверяет ОБЕ грамматики, а не только новое колесо;
- нет таймаута дочернего процесса, 20 повторов и автоматического сравнения baseline;
- при runtime 0.26 стандартный выходной путь — именно
  `glsl_probe_results_runtime26_diagnostic.json`, который план запрещает перезаписывать.

Просто запустить текущий probe недостаточно для приёмки. Это не упрёк плану за
отсутствие готового теста: нужно явно включить создание отдельного приёмочного
runner или доработку диагностического скрипта в разрешённый объём работ.

**Поправка:** runner для одной выбранной грамматики, строго БЕЗ ctypes,
с явным выходным путём, таймаутом, 20 отдельными процессами на каждый из 22 файлов
и ещё 20 процессами минимального повтора. Любое падение, таймаут, пропущенный файл,
ошибка загрузки или несовпадение baseline → FAIL и ненулевой exit code.
Сохранять результаты каждого повтора, а не только последнего. Диагностический JSON
оставить неизменным. Не вводить правило «дерево с ERROR = FAIL»: известные
ERROR/MISSING входят в baseline и должны сравниваться с ним.

## K2 — major: «ближайший коммит» ломает эксперимент с одной переменной

**Адрес:** Plan10, шаг 1, строки 74–76; шаг 2, строка 85; шаг 4.4.

План разрешает взять ближайший коммит и записать расхождение, но одновременно
требует оставить грамматику прежней и сравнивает результат с опубликованным 1.0.0.
Если изменился parser.c/grammar.js, разница может объясняться грамматикой,
а не исправлением привязки. В установленном wheel есть binding.c и _binding.pyd,
но НЕТ parser.c и grammar.js — сверить их «с тем, что внутри колеса» напрямую нельзя.

Для PyPI 1.0.0 уже имеется точная отправная точка: provenance Windows x64 wheel
на PyPI указывает publishing commit
`3a00d49a88cb53eec519b49d8e234e77d916f8ac`:
[PyPI](https://pypi.org/project/tree-sitter-glsl-spec/),
[commit](https://github.com/Caellian/tree-sitter-glsl/tree/3a00d49a88cb53eec519b49d8e234e77d916f8ac).
Provenance связывает артефакт с публикацией из этого коммита; SHA256 исходников
и diff всё равно нужно записать, а не считать это доказательством идентичности
всех деталей сборки.

**Поправка:** сначала использовать этот коммит и проверить recipe публикации.
В основном эксперименте менять только Python-привязку/необходимую упаковку,
зафиксировав hashes parser.c и grammar.js. Если точное соответствие источников
установить не удалось — честный блокер воспроизводимости либо отдельный вариант
эксперимента, не незаметная замена исходной грамматики.

Также зафиксировать SHA256 всех 22 шейдеров: baseline сейчас содержит имена,
диапазоны и обрезанные фрагменты, но не hashes исходных файлов. При изменении
внешней папки baseline надо повторить на 0.25.2 для текущих байтов и сохранить
отдельно; исторический JSON не перезаписывать.

## K3 — major: доказывать, какое колесо и какой runtime реально проверены

**Адрес:** Plan10, ограничения строк 64–66, шаг 4, сдача и установка колеса.

`--target` + `PYTHONPATH` — подходящий механизм, но сами по себе не доказательство
изоляции. У нашего probe есть дополнительный путь подмены runtime:
`GLSL_PROBE_RUNTIME` (вставляется первым в sys.path). Ошибочное наследование этого
окружения может дать чистый прогон на 0.25.2 вместо требуемого 0.26.0.
Если target не применился в worker, может загрузиться старое колесо из venv.

**Поправка:** в КАЖДОМ worker, до обхода дерева, проверить и записать:

- sys.executable, Python/version/architecture;
- точную версию и путь `tree_sitter`, включая его бинарный модуль;
- путь GLSL-пакета и его бинарного модуля, версию, SHA256 бинарника;
- что GLSL загружен из проверяемого target, runtime — эталонный 0.26.0,
  а `module.language()` возвращает capsule, не int;
- что `GLSL_PROBE_RUNTIME` и другие диагностические подмены отключены.

Новому wheel желательно дать отличимую local version, например
`1.0.0+capsule1`, записать SHA256 и проверять установленную версию после установки.
Если оставить upstream version 1.0.0, явно предусмотреть
`pip install --force-reinstall --no-deps <точный путь wheel>`: обычный pip install
может не заменить уже установленную такую же версию. Это реализационный выбор,
но идентичность проверенного и устанавливаемого артефакта обязательна.

## K4 — уточнение вывода: один чистый C++ контроль не исключает баг 0.26

**Адрес:** Plan10, шаг 4.5, строки 102–103: «исключаем баг самого 0.26».

Успех tree-sitter-cpp показывает работоспособность конкретной контрольной нагрузки.
Он не исключает runtime-баг, зависящий от формы дерева, ERROR/MISSING, числа узлов
или конкретных свойств Node/Point. Иначе можно ошибочно приписать сбой грамматике
лишь потому, что другой язык прошёл.

**Поправка:** оставить C++ контроль, но формулировать вывод как «проверяем, является ли
сбой общим для контрольного обхода». Локализованная причина — отдельное доказательство;
если её не удалось получить, допустимый итог: «причина не локализована», wheel
не принят. Успех 20 повторов — критерий данного эксперимента, не доказательство
отсутствия любых нативных ошибок.

не запускался). Он настраивает компилятор командой:

```bat

```

cmd, чтобы сохранить PATH/INCLUDE/LIB. CUDA/CMake-часть примера к wheel не относится.
