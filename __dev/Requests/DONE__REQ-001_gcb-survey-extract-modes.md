**Автор контекста:** Hermes agent — потребитель утилиты в задаче «Hermes self-undo» (исследование ~24 выдёргивания из god-файлов на 6–20k строк)

## 1. Суть запроса одной фразой

Добавить в `gcb` **batch-координатный режим**: один вызов принимает массив точек (`file:line`) и возвращает либо **карту** («где это живёт» — лестница до lvl 1 с именами и рейнджами), либо **тела** обхватывающих блоков на заданных уровнях; при этом формат вывода зафиксировать как **стабильный контракт**, который другие тулы экосистемы переиспользуют (стиль вывода + общая система флагов: одно имя = одно поведение).

## 2. Почему (боль потребителя, реальный кейс)

Workflow в исследовательской задаче всегда двухфазный:

1. **Discovery:** grep → N попаданий `file:line` (часто много в одном файле).
2. **Ориентация:** для каждого попадания — «в каком именованном объекте это живёт?» Сегодня = N отдельных вызовов `--query --ancestor-level K`.
3. **Извлечение:** выбор 3–5 объектов → тела блоков.

Боль: фаза 2 размазана на N раундов; god-функции (`run_conversation` 6571 строк, `_execute_tool_calls_sequential` ~800) нельзя тянуть целиком — нужно знать размер **до** извлечения.

## 3. Симуляция (реальные данные, не гипотезы)

### Кейс A: grep дал 4 попадания в `cli.py` → один вызов вместо четырёх

Вход:
```
gcb --file /workspace/SRC/hermes-agent-src/cli.py --lines 1001,1240,1268,1279
```
Ожидаемый вывод (данные из реальных прогонов текущего билда):
```
#File: /workspace/SRC/hermes-agent-src/cli.py (20400 lines) · 4 hits
[1/4] hit 1001 — top-level, no ladder:
     lvl 1 [1-20400] <module>   → _active_agent_ref = None
[2/4] hit 1240:
     lvl 3 [1237-1246] if notify_session_finalize:
     lvl 2 [1193-1283] try:
     lvl 1 [1185-1285] def _run_cleanup(*, notify_session_finalize=True):
[3/4] hit 1268: same ladder as [2/4] — _run_cleanup (×2 hits)
[4/4] hit 1279: same ladder as [2/4] — _run_cleanup (×3 hits)
```
**Свойство, которое важно:** режим A **по конструкции не может стать большим** — лестница = max_depth строк на попадание (в Python обычно 3–5), дедуп схлопывает повторы. Вопрос «что если вывод большой» для survey-режима не существует.

### Кейс B: тот же вход + уровни → тела
```
gcb --file .../cli.py --lines 9870,1240 --levels 0,0 --query
```
→ тело `undo_last` [9870-9997] (128 строк) + `_run_cleanup` [1185-1285], каждый с хедером.

### Кейс C: «монстр» виден по одной строке
```
[1/1] hit 7204 in agent/conversation_loop.py:
     lvl 4 [6786-7421] if assistant_message.tool_calls:
     lvl 3 [6510-8145] try:
     lvl 2 [1909-8240] while (api_call_count < agent.max_iterations ...):
     lvl 1 [1691-8261] def run_conversation(        ← 6571 строк, видно сразу
```
По `[1691-8261]` потребитель знает: целиком сюда нельзя — работать по внутренним строкам. Это и есть ответ на «что если объект огромный».

## 4. Спецификация

### 4.1. Режимы (один синтаксис, два поведения)

| Флаги | Режим | Поведение |
|---|---|---|
| `--lines a,b,c` (без `--query`) | **survey** | на каждое попадание: строка внутреннего блока + лестница вверх до lvl 1 с именами и рейнджами; дедуп одинаковых лестниц (`same ladder as [N]`, счётчик `×K hits`) |
| `--lines ... --levels l1,l2,... --query` | **extract** | тело блока на уровне `li` от i-го попадания (0 = внутренний, 1 = родитель — семантика совпадает с существующим `--ancestor-level`); хедер у каждого тела |
| `--head N` | модификатор extract | только первые N строк каждого блока. Самый частый кейс потребителя: сигнатуры 5–6 функций за один вызов |

Синтаксис пар `line:level` (вместо двух массивов) — приемлемая альтернатива, на выбор разработчика; семантика та же.

### 4.2. Политика больших размеров (решение заказчика, фиксация)

Утилита **не отдаёт огромные простыни по умолчанию**:
- выдаёт **начало** блока (~40 строк — число на калибровку);
- маркер: `# TRUNCATED: block is N lines total; add --force for full body`;
- `--force` → полное тело без капа, включая монстров (класс на 12k строк) и большие карты (outline объекта, где только методы lvl 2 = 250 строк).

Т.е. усечение **одностороннее** (head), не head+tail: хвост — это то, что потребитель добьёт целевым `--line` во внутреннюю строку. Маркер обязателен и содержит точный размер блока — вывод остаётся навигируемым без повторного вызова.

### 4.3. Надёжность батча
- `[i/n]` индексация каждого элемента;
- ошибка в одном элементе не роняет батч: `[3/4] ERROR: no named block at line N`, остальные элементы приходят;
- итоговая строка статуса: `# 3 ok, 1 error`.

### 4.4. Формат вывода = контракт (важнейший пункт для экосистемы)

Фиксировать как стабильный API:
1. **Самоидентификация блока:** первая строка каждого блока — `#File: <абсолютный путь>` + `#Block level: K range: A-B  <имя>`. Конкатенация произвольного числа блоков остаётся разборчивой без внешнего контекста (это уже есть в билде — сохранить).
2. **Метаданные — только comment-prefixed строки** (`#...`) — парсятся любым тулом одним правилом; тело блока никогда не начинается с `#`-метаданных утилиты.
3. **Чистый вывод при pipe** (без TTY-подсказок) — уже есть, зафиксировать в контракте.
4. Не ломать: любые изменения формата — только мажорная версия контракта.

### 4.5. Общее словари флагов экосистемы (предложение)

Одно имя = одно поведение во всех тулах пакета:

| Флаг | Значение везде |
|---|---|
| `--file` | цель; **абсолютный путь — канонический адрес** (relative-резолв через PROJECT_ROOT оставляем как фичу, но документировать: для программных потребителей абсолютные пути) |
| `--lines` / `--line` | координаты (массив/одна) |
| `--level` / `--ancestor-level` | два масштаба адресации (абсолютный от верха / относительный вверх) — текущая семантика gcb, распространить на все тулы с блоками |
| `--query` | «дай точное тело», без него — карта/обзор |
| `--head N` | первые N строк каждого элемента |
| `--force` | отключить капы размера (полные тела/карты) |
| `--outline`, `--level K` (в outline-режиме) | структура файла с cap глубины — текущая семантика gcb |

## 5. Интеграция с discovery (перспектива, не blocking)

Идея заказчика: новый grep-тул пакета получит флаг `--gcb` — режим, где результат поиска сразу отдаётся в формате §3 кейса A (что нашлось + лестница «где живёт» для каждого попадания). Т.е. конвейер **discovery → context map** становится одним вызовом:

```
newgrep -rnF 'pattern' --gcb <dir>   # = grep-попадания, каждое с лестницей до именованного объекта
```
Для этого достаточно: grep отдаёт `file:line` списком → gcb batch-режим (§4.1) принимает его как вход (stdin или аргументы). Это и есть «центральный тул, раздающий API»: поиск — глаза, gcb — руки, формат §4.4 — общий язык.

## 6. Acceptance criteria (прогон на реальных данных этой задачи)

1. `gcb --file /workspace/SRC/hermes-agent-src/cli.py --lines 1001,1240,1268,1279` → вывод как в §3 кейс A, ≤ ~15 строк, с дедупом `[3/4]`, `[4/4]`.
2. `gcb --file /workspace/SRC/hermes-agent-src/cli.py --lines 9870 --levels 0 --query` → полное тело `undo_last` [9870-9997], 128 строк (здесь блок < капа — без маркера).
3. Блок > капа: extract на 6571-строчный `run_conversation` **без** `--force` → ~40 строк + маркер с точным размером; **с** `--force` → всё.
4. Плохая строка в батче (`--lines 9870,99999`) → `[1/2]` ок, `[2/2] ERROR`, exit-код ≠ 0, но тело первого блока на месте.
5. `--head 3` на 6 сигнатур за один вызов → 6 хедеров + по 3 строки тел, без единого маркера TRUNCATED (кап не срабатывает — запрос осознанный).

## 7. Чего НЕ просим
- Именное извлечение («найди объявление по имени») — отдельный будущий REQ; здесь только координаты.
- Spill на диск, мультифайловые батчи в одном вызове (мультифайл = несколько `--file` или интеграция §5) — не блокирует текущую пользу.

## 8. Решение (обсуждение с потребителем/пользователем, 2026-08-23)

**Область.** Батч трогает ТОЛЬКО вывод `gcb` (структурирование, избежание стен). `read`/`patch`/
бухгалтер (BRAINSTORM) — не строим сейчас, это отдельный слой поверх. Капы размера (§4.2, ~40 строк
+ `--force`) — идея БЕТОННАЯ (остаётся целью), но механики пока нет; путь дегрaдации —
**структурный** (карта/оглавление скрытых детей + счётчик), НЕ текстовое усечение головы блока.
Счётчик спрятанного — двухуровневый: ПЕР-ОБЪЕКТНЫЙ («у этого класса спрятано 64 метода») + ОДНА
итоговая сумма по всему дереву («34 строки спрятано суммарно, добавь `--force`»). Строится ПОСЛЕ
батч-режима, отдельным заходом.

**Батч подтверждён, синтаксис:**
- `--line` принимает массив (`--line 1827,606,867`) — один вызов, один парс.
- Три режима-глагола: голая лестница (survey, дедуп одинаковых лестниц `same ladder as [N] ×K`),
  `--outline --line …` (объединённое дедуп-дерево, эскалация по `--level`), `--query --line …`
  (+ `--level`/`--ancestor-level`) (тела по каждому хиту, `[i/n]`, ошибка одного не роняет батч).
- **НЕТ нового имени флага для батч-адресации** (правка §4.1: там было предложено `--levels` —
  отдельное множественное имя. Убрано.) Существующие `--level` (АБСОЛЮТНЫЙ адрес от верха файла) и
  `--ancestor-level` (ОТНОСИТЕЛЬНЫЙ, вверх от точки попадания — то, что §4.1 в исходном REQ назвало
  "0=внутренний, 1=родитель") — как и раньше, два разных флага с разной семантикой, никогда не
  смешиваются. Просто ОБА теперь дополнительно принимают массив (`--ancestor-level 0,1,0`), когда
  `--line` — массив. Одно число вместо массива размножается на все хиты; массив короче `--line` —
  последнее значение размножается на остаток; длиннее — лишнее игнорируется.
- **`--head` — НЕ делаем.** Избыточен: `--outline` уже даёт заголовки объектов (как оглавление
  книги) для каждого попадания — ровно та задача, для которой `--head` предлагался (grep приводит
  в файл/строку, `--outline` называет объект, в который попали).
- **Новых имён флагов в этом REQ, помимо будущего `--force` (§4.2, механики пока нет), НЕТ** — весь
  батч выражается через существующие `--line`/`--level`/`--ancestor-level`/`--outline`/`--query`,
  просто научившиеся принимать массив.

**Диапазоны (`--line a-b`) — рассмотрели, осознанно УБРАЛИ из этого REQ.** Идея: диапазон — не
"точка", а запрос "для каждой строки от a до b — имя блока, к которому она принадлежит,
декомпозиция диапазона на соседние блоки ОДНОГО уровня" (не единый охватывающий контейнер).
Крайний случай — a и b в двух НИКАК не связанных top-level объектах: по идее выдаём как есть
(в будущем — то же самое правило капа/`--force`, что и везде). Решили, что это плохой,
перегруженный краевыми случаями сценарий для v1 (быстро скатывается в отдельную мини-фичу "partial outline slice"
со своими краевыми случаями) — убираем из объёма REQ-001, оставляем этот абзац как след мысли для
будущего REQ, если понадобится.

**Проверено (2026-08-23): `--outline` НЕ обрезает длинные объявления.** Опасение было — не режем
ли мы многострочные сигнатуры/декларации в лейбле outline-строки. Проверила на реальной 8-строчной
сигнатуре (`_rerank_once` в `test/pythonSRC/backends/rerank_driver.py:49`, параметры на нескольких
строках) — `--outline` вывел её ПОЛНОСТЬЮ, ни один параметр не пропал. В коде единственный `cap`
(60 символов) — только у comment-полос (`_first_comment_line`), не у деклараций; `name()` для
def/class не режет вообще. Ничего чинить не нужно.

**Acceptance criteria (§6 исходного REQ) — свои, не берём готовыми.** Часть из них (AC3, AC5)
завязана на `--force`/капы, которых пока нет — когда дойдём до реализации, распишем критерии под
то, что реально строим в v1 (batch survey/outline/query без капов), а капы — отдельным заходом со
своими критериями.
