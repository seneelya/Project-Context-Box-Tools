## 1. Суть одной фразой

Три мелких, но кусачих расхождения, найденных при первом реальном деплое: `--file` означает разное
в разных тулах пакета, `check_cards_freshness` молча выдумывает корень проекта, и свежесозданный
`CONFIG__TOOLS.py` приезжает с путями ЧУЖОГО проекта.

## 2. Находка A — `--file` разрешается от разных баз (главное)

REQ-001 §4.5 уже зафиксировал принцип: **одно имя флага = одно поведение во всех тулах пакета.**
Сегодня он нарушен именно на `--file`:

| Тул | От чего считается относительный путь |
|---|---|
| `find_code_usage.py --file` | от `CONFIG__TOOLS.PROJECT_ROOT` |
| `get_codeblock.py --file` | от **cwd** |
| `show_pyfile_api.py <file>` | от **cwd** |

Как это выглядит живьём (cwd = `<project>/__HQ/tools/`, `PROJECT_ROOT` = корень проекта):

```
python get_codeblock.py    --file ../../file_ops/_new_format.py   # OK
python show_pyfile_api.py         ../../file_ops/_drift.py        # OK
python find_code_usage.py  --file ../../file_ops/_new_format.py
  -> Error: --file does not exist or is not a file: T:\file_ops\_new_format.py
python find_code_usage.py  --file file_ops/_new_format.py         # OK
```

То есть один и тот же путь работает ровно в половине тулов, а сообщение об ошибке показывает
склеенный путь и этим спасает — но только потому, что путь вылез за корень диска и стал заметен.
Внутри большого дерева такая склейка может попасть в СУЩЕСТВУЮЩИЙ файл, и тогда тул тихо
отработает не по тому файлу. Вот это и есть настоящая опасность, а не неудобство.

**Чего просим:** одно правило на весь пакет, объявленное в `TOOLS.md`. Предпочтительное (но решает
разработчик): относительный путь считать от **cwd** — это то, чего ждёт человек и что уже делают
два тула из трёх; `PROJECT_ROOT` остаётся базой для *сканирования* (обратный индекс, `--all`,
`TEST_DIRS`), а не для адресации цели. Абсолютный путь везде канонический — как REQ-001 §4.5 и
говорит.

Если решение будет обратным (всё от `PROJECT_ROOT`) — это тоже приемлемо, но тогда нужен внятный
отказ вместо склейки: «путь вне PROJECT_ROOT» отдельным сообщением, а не молчаливый join.

## 3. Находка B — `check_cards_freshness` выводит корень проекта из папки карточек

`check_cards_freshness.py:172`:

```python
project_root = args.project_root.resolve() if args.project_root else cards_dir.parent
```

`cards_dir` по умолчанию — `__map` относительно cwd. Запуск из `__HQ/tools/` (а это ровно то место,
откуда естественно запускать тул) даёт `project=<...>/__HQ/tools` и бодрый вывод:

```
cards=__map project=T:\AgentsWork\hermes-filetools\__HQ\tools mode=mtime
total=0 fresh=0 outdated=0 orphan=0
no cards found
```

Формально всё честно, но читается как «карточек в проекте нет», хотя тул просто смотрел не туда.
Из корня проекта тот же вызов даёт `project=<корень> mode=git` — правильно.

**Чего просим:** если `__map` не найден, сказать это отдельно от «нет карточек» — то есть различить
«папки карточек нет по этому пути» и «папка есть, карточек в ней нет». Заодно — определять корень
поиском вверх до `.git`/`__HQ`, а не через `cards_dir.parent`.

## 4. Находка C — сид `CONFIG__TOOLS.py` содержит пути чужого проекта

`deploy_hq.py --init` сеет `__HQ/tools/CONFIG__TOOLS.py` копированием из шаблона, а в шаблоне лежит
рабочий конфиг **memohood**:

```python
PROJECT_ROOT = _resolve_root([
    "/workspace/SRC/memohood",
    r"Y:\Hermess\body\sandboxes\docker\default\workspace\SRC\memohood",
]) or "."
```

плюс докстринг `"""Shared configuration for tools in /project/tools directory."""` — путь, которого
в схеме нет (тулы живут в `__HQ/tools/`), и примеры в комментариях тоже на memohood.

Опасность не в мусоре, а в `_resolve_root`: он возвращает **первый существующий** путь. Развернём
скелет на машине, где каталог memohood существует, — и новый проект молча получит корнем ЧУЖОЙ
проект. Ошибка при этом не всплывёт: тулы отработают, просто по другому дереву.

**Чего просим:** сеять нейтральную заготовку — пустой список кандидатов с комментарием-примером
(`# "/project/<your-project>", r"C:\path\to\<your-project>"`), докстринг про `__HQ/tools/`, примеры
в `TEST_DIRS` обезличенные. Опционально: `deploy_hq.py --init` печатает «заполни
`__HQ/tools/CONFIG__TOOLS.py`» в списке скаффолдов — сейчас факт, что файл требует ручной правки,
нигде не сказан.

## 4.5 Находка D — `BLACKLIST_DIRS` не читался при сканировании (ЗАКРЫТА 2026-08-26)

Ключ `BLACKLIST_DIRS` читал только `replace_in_files.py` (по компонентам пути). Сканирование
(`find_code_usage/core.py::collect_files` → `should_include_dir`) фильтровало по хардкоду
`EXCLUDED_DIRS` и конфиг игнорировало. Следствие: каталог, исключённый в конфиге проекта, всё равно
попадал в обратный индекс и получал карточку от `make_interface_card --all`.

Важная поправка к первой редакции этого REQ: я написала «мёртвый конфиг» — **неверно**, у ключа был
живой потребитель. Мёртвой была только половина: значение соблюдалось при ЗАПИСИ и игнорировалось
при СКАНИРОВАНИИ. Это опаснее полной неработоспособности: конфиг выглядит действующим, потому что в
одном туле он действительно действует.

Починено: `should_include_dir` дополнительно сверяется с `CONFIG__TOOLS.BLACKLIST_DIRS`, матч по
КОМПОНЕНТУ пути — та же семантика, что уже была у `replace_in_files`, чтобы одно значение конфига не
означало разного в зависимости от того, кто его прочитал. Разрешается один раз и кешируется; любой
сбой импорта даёт пустое множество, поэтому проект без конфига сканируется в точности как раньше.

## 5. Acceptance criteria

1. `TOOLS.md` содержит один явный абзац «как разрешаются пути» и все три тула ему следуют.
2. Относительный путь, уводящий за пределы допустимой базы, даёт внятную ошибку, а не молчаливую
   склейку, которая может попасть в существующий файл.
3. `check_cards_freshness` из любой папки проекта либо находит корень, либо честно говорит, что
   папки карточек по этому пути нет — и это сообщение отличается от «карточек нет».
4. Свежий `--init` на машине с посторонним каталогом memohood НЕ подхватывает его как
   `PROJECT_ROOT`.

## 6. Чего НЕ просим

- Не просим менять семантику `--level`/`--ancestor-level`/`--query`/`--outline` — они как раз
  единообразны, к ним претензий нет.
- Не просим авто-детект корня внутри каждого тула как замену `CONFIG__TOOLS` — конфиг остаётся
  единственным источником правды, речь только о том, ЧТО от него отсчитывается.
