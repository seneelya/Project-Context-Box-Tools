# REQ-003 · find_code_usage: цель во ВЛОЖЕННОМ пакете не находит своих консьюмеров

**Статус:** ОТКРЫТ, 2026-08-26. Отложен осознанно — не блокер, но делает карточки вложенных
пакетов недостоверными.
**Автор контекста:** Соня5 — первое построение `__map/` на живом проекте (`hermes-filetools`,
23 карточки).
**Дата:** 2026-08-26

---

## 1. Суть одной фразой

Если целевой файл лежит НЕ на верхнем уровне проекта, а во вложенном пакете, то `from . import X`
у его соседей не распознаётся как использование — и все публичные имена такого файла штампуются
`consumers 0`, хотя они реально вызываются.

## 2. Как обнаружено

В `hermes-filetools` есть второй, независимый плагин `self_delegate/plugin/self-delegate/`.
После заполнения карточек ВСЕ публичные имена `delegate_core.py` оказались `consumers 0`, хотя
`self_delegate/plugin/self-delegate/__init__.py` вызывает их десяток раз:

```python
from . import delegate_core          # :27
...
result = delegate_core.pop_ack(args)  # :86
delegate_core.mark_incompatible()     # :163
delegate_core.prepare_self_delegate(assistant_message, self, messages)  # :172
```

Сначала это списали на «атрибутный доступ к модулю не отслеживается». **Неверно** — отслеживается:
в `file_ops` ровно такая же форма (`view_file_new_core.view_file_tool_new(...)`) находится штатно,
это и есть путь `fallback` в выводе тула. Причина другая.

## 3. Причина (найдена, не гипотеза)

Две части, обе воспроизводятся в одну строку кода.

**3.1 `matches_target` сверяет цель только как ПРЕФИКС.**
`find_code_usage/handlers/python_handler.py::matches_target` (≈36-47) возвращает True, когда
импортированный модуль РАВЕН цели или НАЧИНАЕТСЯ с `цель + "."`. Формы «цель как хвост» —
`пакет.цель` — нет вообще:

```
matches_target('delegate_core',               {'delegate_core'}) -> True
matches_target('self-delegate.delegate_core', {'delegate_core'}) -> False   # <- вот оно
matches_target('self-delegate',               {'delegate_core'}) -> False
```

**3.2 `from . import X` по построению даёт `<пакет>.X`.**
В `analyze_file` для from-import считается `resolved_base = resolve_relative_import(...)`, затем
`full_module_path = f"{resolved_base}.{original_name}"`. Для `from . import delegate_core` из
`self_delegate/plugin/self-delegate/__init__.py`:

```
dots=1, module='' -> resolved base = 'self-delegate'
full_module_path        = 'self-delegate.delegate_core'
target_names            = {'delegate_core', ...}      -> не совпало
```

**Почему `file_ops` не страдает.** Он лежит на ВЕРХНЕМ уровне проекта, поэтому
`resolve_relative_import` отдаёт `file_ops` — и это одновременно и имя каталога, и полный путь от
корня. `full_module_path` выходит `file_ops.view_file_core`, а `target_names` для цели содержит
ровно эту дотированную форму, и срабатывает ветка `normalized`. Стоит цели уйти на уровень глубже —
`resolved_base` остаётся ПОСЛЕДНИМ каталогом, а не путём от корня, и совпадение рассыпается.

То есть баг не в дефисе имени `self-delegate` и не в атрибутном доступе. Он в том, что
`resolve_relative_import` возвращает имя каталога вместо root-relative пути, а `matches_target` не
умеет матчить хвост.

## 4. Почему это важнее, чем выглядит

Симптом — не пустое место, а НЕВЕРНЫЙ ФАКТ: `consumers 0` читается как «это никто не использует,
можно удалять». Карточка существует, чтобы ей верили ВМЕСТО исходника, поэтому тихо занижённый
счётчик хуже отсутствующей карточки. Ровно этот же класс ошибки уже был закрыт в
`__HQ/tools` @ `1632eaf` (два бага разбора импортов), и он же — единственная причина, по которой
на 23 карточках вообще пришлось перепроверять факты руками.

## 5. Варианты решения (на выбор разработчика)

1. **Матчить хвост в `matches_target`** — принимать `imported_module.endswith("." + tn)`. Дёшево,
   одна строка. Риск: ложные срабатывания на одноимённых модулях из разных пакетов
   (`a.utils` зачтётся цели `b/utils.py`). Для проекта без дублей имён приемлемо, как общее
   решение — нет.
2. **Сделать `resolve_relative_import` root-relative** — возвращать путь от корня проекта
   (`self_delegate/plugin/self-delegate`), а не последний каталог. Правильно по существу, но
   дороже: дотированная форма для каталога с дефисом — фикция (это не валидный Python-идентификатор),
   значит сравнивать надо ПУТЯМИ, а не дотами.
3. **Сравнивать разрешённые ПУТИ вместо имён** — резолвить и импорт, и цель до абсолютного пути
   файла и сверять их. Самое надёжное и снимает заодно дефисы; самое большое по объёму.

Моя рекомендация: 3 как цель, 1 НЕ делать даже как временную меру — ложный `consumers` хуже
нулевого, а вариант 1 их создаёт.

## 6. Acceptance criteria

1. `find_code_usage --file self_delegate/plugin/self-delegate/delegate_core.py` находит
   `__init__.py` как консьюмера (сейчас — `# No external usages found.`).
2. Работает при любой глубине вложенности, а не только на два уровня.
3. Каталог с дефисом в имени (не валидный Python-идентификатор) не ломает разрешение.
4. Два одноимённых модуля в РАЗНЫХ пакетах не зачитываются друг другу как консьюмеры.
5. Регрессия зелёная: `test/check.py`, `test/golden_check.py`.

## 7. Чего НЕ просим

- Не просим трогать разбор импортов, починенный в `1632eaf` (скобочные импорты + хвостовой
  комментарий) — там всё верно, это другой слой.
- Не просим отслеживать динамический доступ (`getattr`, `importlib`) — отдельная тема.

## 8. Оговорка про объём проблемы

На момент находки задеты только `self_delegate/**` — 3 файла припаркованного плагина. Все 20
карточек `file_ops` корректны, потому что пакет лежит на верхнем уровне. Так что это не пожар, а
мина: она сработает у первого же проекта со нормальной вложенной структурой (`src/pkg/sub/mod.py`),
где ВСЕ карточки будут показывать `consumers 0`.
