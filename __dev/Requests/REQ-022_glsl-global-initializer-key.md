# REQ-022 — GLSL: глобальная переменная с инициализатором в скобках теряет ключ при перештамповке

## Что видно

contact_lab, 18 Nov 2026, карточка `shaders/batch_approach.glsl` (формат 1.5.0, штамп после REQ-021). Агент заполнил
прозу и перештамповал карточку; две записи не нашли своего места:

```
NEW — fill prose: g_fr_rel, g_ap_have
SALVAGED — removed from code, moved to '## Salvage': dvec3, bool
```

Записи:

```
#### `dvec3 g_fr_rel = dvec3(0)`
#### `bool g_ap_have[3] = bool[3](false, false, false)`
```

Проза ушла в `## Salvage` под ключами `dvec3` и `bool`, а у записей снова `<|fillN|>`. Соседние глобальные переменные с
инициализатором без скобок (`uint g_ap_mode = 0u`, `double g_ap_h = 1.0LF`, `bool g_fr_open = false`) сливаются
нормально. Похоже, ключ записи при разборе старой карточки берётся неверно, когда в инициализаторе есть `(...)`: имя
теряется, остаётся тип.

Обход в contact_lab: проза вписана руками, `## Salvage` удалён (коммит проекта `8f7d1f6`). При следующей
перештамповке ошибка повторится.

## Что просим

Ключ записи глобальной переменной GLSL — её имя, при любом инициализаторе (вызов конструктора, массив
`T[N](...)`, вложенные скобки). Проверить и другие формы: `const dvec3 X = dvec3(...)`, `shared`-массивы.

## Проверка

Фикстура `test/secret/contact_lab_shaders/batch_approach.glsl` — её нет в наборе, при надобности скопировать из
проекта в `test/secret/` (приватно). Синтетика для коммитящихся тестов: глобальные `dvec3 a = dvec3(0);` и
`bool b[3] = bool[3](false, false, false);` с прозой; перештамповка — `prose kept` для обеих, без `## Salvage`.
