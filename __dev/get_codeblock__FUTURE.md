# get_codeblock — FUTURE: top-level именованные литералы-константы не видны

## Проблема (столкнулась 18.08, реальный код, не синтетика)

В `hermes-agent-src/tools/file_tools.py` есть модульные константы-схемы:

```python
READ_FILE_SCHEMA = {
    "name": "read_file",
    "description": "...",
    "parameters": { ... },
}

WRITE_FILE_SCHEMA = {
    ...
}
```

`get_codeblock --file file_tools.py --line 2652 --query` (строка самого `READ_FILE_SCHEMA = {`) —
**не отдаёт этот блок**. Вместо него ладдер резолвится либо к пустому top-level (нет объемлющего
блока — Python-хендлер индентационный, а не bracket-based), либо соскальзывает на соседнюю функцию.
`--outline` тоже не показывает `READ_FILE_SCHEMA`/`WRITE_FILE_SCHEMA` вообще — они инвизибл, хотя это
ровно те опорные точки, по которым человек/агент ищет "где схема тула".

## Почему это важно

- `SCREAMING_SNAKE_CASE` на верхнем уровне модуля — это **сигнал важности** сам по себе (конвенция:
  константа/конфиг/таблица), не просто переменная. Инструмент, который выдаёт карту файла, должен
  показывать такие вещи первым делом — сейчас показывает функции/классы, но не их.
- Формально это тот же паттерн, что уже решён для JS/TS в `_ARROW_BINDINGS`
  (`const Foo = () => {…}` — именованный блок по имени привязки), просто:
  1. не покрывает **литералы без функции** (`const FOO = {...}` / `[...]` без `=>`) — не проверено,
     нужно перепроверить, попадает ли туда сейчас plain-object-литерал без arrow;
  2. **вообще не существует для Python** — Python-хендлер строит блоки только из отступных `suite`
     (`def`/`class`/`if`/`for`/...); многострочный `{...}`/`[...]`/`(...)` внутри одного logical
     statement (bracket-continuation) — это не отступное вложение, у него нет "суда" в текущей модели
     вообще. Питоновский хендлер сегодня физически не может увидеть такой блок, не только не
     показывает его в outline.

## Куда это ведёт — черновой дизайн

Нужен третий вид "блока" в добавление к текущим двум (indentation-suite для Python; brace-body для
tree-sitter языков): **bracket-continuation литерал, привязанный к имени присваивания**, на
top-level или внутри класса/функции.

Правило (первый набросок):
- Триггер: `NAME = <bracket>` (или `NAME: Type = <bracket>` — аннотированное), где `<bracket>` —
  `{`/`[`/`(` и закрывающая скобка находится на **другой** физической строке (многострочный литерал).
  Однострочный `X = {"a": 1}` — не блок (симметрично правилу "однострочный `{…}` — не блок").
- Границы: не отступом, а **балансом скобок** от открывающей до закрывающей (тот же механизм, что
  `_scan_line_for_braces`/старая brace-nav в `typescript_handler.py` — можно унести в общий хелпер).
- Label: имя присваивания как есть (`READ_FILE_SCHEMA`, не "dict literal") — тот же принцип, что уже
  работает у `_ARROW_BINDINGS` для `const Foo = () => {…}` → `const Foo =`.
- Outline: показывать всегда (это заведомо "именованное"), независимо от `SCREAMING_CASE` или
  `snake_case` — регистр имени не должен быть частью парсер-логики (это семантика имени, не структура
  кода). Но: возможно стоит **визуально выделить** `SCREAMING_CASE` константы в outline отдельной
  меткой (`const` / `⚑` / что-то короткое) — не как условие видимости, а как читаемость: агент,
  скроллящий outline большого файла, сразу видит "вот тут таблица констант", а не гадает по метке
  `{...} object`.
- Применимо везде одинаково: Python (новый механизм, скобочный, отдельно от indentation-суда) и
  tree-sitter языки (обобщить/проверить `_ARROW_BINDINGS`, убрать ограничение "только arrow-bodied",
  если оно там есть).
