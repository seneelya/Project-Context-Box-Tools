# Vision 07: Runtime seams — a machine-readable table for connections the import graph can't see

**Дата:** 2026-09-13. **Статус:** брейншторм — направление зафиксировано через долгое обсуждение,
формат в основном устоялся, но это ВИЖЕН, не план реализации. Открытые вопросы — в конце, честно
непроработаны.

## Зачем

`graph_from_cards.py` строит рёбра только из импортов. Всё, что связывает модули В РАНТАЙМЕ —
динамическая загрузка по вычисленному пути, HTTP между процессами/половинами проекта, общий файл
между двумя ОС-процессами, шина событий — для графа не существует. Карта из N модулей превращается
в несколько несвязанных «островов», хотя связный граф на деле один.

**Цена уже уплачена, реально.** В `hermes-filetools` есть живой инцидент: новый вид записи в
журнале (`_ledger.py`) сломал `dashboard/plugin_api.py`, который читает этот журнал **по пути**
(`spec_from_file_location`), а не импортом — граф в тот момент показывал `plugin_api.py` листом без
единого ребра. Опус (агент, работавший над картой до этой сессии) вручную вписал пометки
`RUNTIME SEAM` прозой в `Doc links` восьми карточек как обходной путь — это и есть мотивирующий
живой пример, на котором строился весь дизайн ниже (не выдумано заранее, а выведено из реальных
формулировок).

Восемь карточек с текущими pyсяными пометками (`hermes-filetools`, найдены грепом
`RUNTIME SEAM`): `context_ctl/_select.py`, `context_ctl/_signal.py`, `dashboard/plugin_api.py`,
`desktop/src/adapter.js`, `desktop/src/core.js`, `desktop/src/prompt-mirror.js`,
`file_ops/_ledger.py`, `file_ops/_msgindex.py`. Они НЕ мигрируют в новый формат автоматически —
свободный текст в структурированную таблицу инструмент превратить не может; кто-то (агент, читая
исходники заново) должен переписать эти 8 карточек руками под новый формат, когда он появится.

## Формат секции

Новая опциональная H2-секция `## Runtime seams`. Появляется в карточке ТОЛЬКО если в ней реально
есть что описывать — никогда не штампуется пустографом с директивой во всех карточках подряд (тот
же урок, что REQ-009: пустая директива, которая возвращается на каждый штамп, обесценивает
«awaiting agent» как статус).

```
## Runtime seams

Contract: `python __HQ/tools/make_interface_card.py --help-seams` (columns, Kind/Shape vocab, examples).

| Target | Symbol | Kind | Shape | Why |
|---|---|---|---|---|
| `promo_engine.py` | `apply_discount` | by-path | dependent | loaded by feature flag; signature must match |
```

**Уже git-friendly бесплатно.** Это markdown-таблица — одна строка = одна физическая строка файла,
ровно тот же приём, что Plan02 применил к `Dependencies Internal`. Секцию целиком пишет ЛЛМ (не
штамп), и если два человека на разных ветках добавят РАЗНЫЕ строки — это две разные строки файла,
не одна и та же правка одной строки; git сводит сам. Ничего дополнительно делать не нужно, это
свойство уже есть просто из того, что формат — таблица.

**Строка-контракт перед таблицей — ФАКТ, не проза.** Штамп пишет и перезаписывает её на каждом
проходе (как строку версии карточки, Plan02 pt.0) — агент её не редактирует и НЕ удаляет. Смысл:
при первом взгляде на карточку с этой секцией сразу видно «здесь есть контракт», и куда идти за
деталями, если забыл. Полный текст контракта живёт ТОЛЬКО в самом тул-флаге (`--help-seams`), не в
отдельном doc-файле — единый источник истины, не может протухнуть отдельно от кода.

**Колонки Target/Symbol — раздельные, как в `Dependencies Internal` (`File Path`/`Symbols`), не
смешанные в одну строку через `::`/`.`/etc.** Обсуждали смешанное представление (`file::symbol`,
мермейд-узел с обоими сразу) — отклонено: не язык-агностично, создаёт путаницу для модели-автора,
а раздельные колонки решают это бесплатно, мы это уже делаем в другом месте формата.

## Kind (канал) — закрытый список, 4 значения

Не 5 — `by-path` и `process` изначально казались разными (см. историю обсуждения ниже), но это
ОДНА ось «каким каналом», просто с разными типичными контрактами поломки:

- **`by-path`** — динамическая загрузка модуля/файла по вычисленному пути, в ТОМ ЖЕ процессе
  (Python `spec_from_file_location`/`importlib.import_module(computed)`, аналоги в других языках —
  Java-рефлексия, `require(computed)` в Node). Что ломается — сигнатура/API загруженного объекта.
- **`process`** — запуск/управление ОТДЕЛЬНЫМ ОС-процессом (`subprocess.run`, `os.system`,
  `child_process.spawn`). Что ломается — CLI-контракт (аргументы/stdout/exit-код), не сигнатура.
  Если ПОСЛЕ запуска есть ещё содержательный обмен данными через отдельный канал — это ВТОРАЯ
  отдельная строка (`file`/`http`/…) на ту же цель, не встроенная пометка внутри строки `process`.
- **`http`** — сетевой вызов (REST/любой транспорт, который может обратиться к чему угодно).
- **`file`** — общее персистентное хранилище (файл, строка/таблица БД, in-memory общий стор — по
  сути одно и то же: кто-то пишет, кто-то читает, импорта нет). Требует суффикс направления
  (см. ниже) — «кто пишет, кто читает» НЕ следует из того, чья это карточка.
- **`event`** — шина/паб-саб/вебсокет. Тоже требует суффикс направления — эмиттер и консьюмер
  РАЗНЫЕ файлы, и оба могут захотеть написать свою строку про одно и то же имя события.

`env` (общая переменная окружения как неявный контракт) — рассмотрели и ОТКЛОНИЛИ как отдельный
Kind: это не канал, а обычно `reference`-форма связи, которая едет поверх уже существующего канала
(файла/процесса), самостоятельной категории не заслуживает.

### Направление — суффикс в Kind, не отдельный столбец

`http`, `process`, `by-path` — направление уже однозначно по конвенции «строку пишет
инициатор/загрузчик» (см. ниже). `file`/`event` — неоднозначны без явной пометки:
- `file:reads` / `file:writes` / `file:reads+writes`
- `event:emits` / `event:listens`

## Shape (форма связи) — закрытый список, 3 значения

Независимая ось от Kind — один и тот же Kind может быть любой из трёх форм (проверено на всех
четырёх Kind во время обсуждения, ни одна комбинация логически не запрещена, валидатор не должен
их жёстко ограничивать).

- **Зависимая (`dependent`)** — исчезновение/смена цели ЛОМАЕТ зависимую сторону; цель может не
  знать о зависимой стороне вообще.
- **Равноправная (`equal`)** — обе стороны завязаны на общий контракт/формат; смена формы ЛЮБОЙ
  стороны ломает ОБЕИХ, ничьей стороны без потерь нет (пример: общий формат `_select.py`, пишет
  панель, читает движок — ни одна сторона не главнее).
- **Справочная (`reference`)** — исчезновение цели НЕ ломает ничего, теряется только контекст/
  наблюдаемость для человека.

**Рабочий тест (сформулирован в обсуждении, это и есть операционное определение на будущее):**
сломается ли что-то реально, если цель исчезнет? Да, у одной стороны → `dependent`. Да, у обеих →
`equal`. Нет, ничего → `reference`.

## Направление объявления — «кто пишет строку»

Как и с обычными импортами (`Dependencies Internal` заполняет импортирующая сторона, граф сам
считает обратные `←`), здесь строку пишет **зависимая/потребляющая сторона** — не обе стороны
руками (риск разъехаться). Механика:
- `http`/`process`/`by-path` — направление уже однозначно (инициатор/загрузчик = тот, чья
  карточка).
- `file`/`equal` без чёткой «более зависимой» стороны — можно объявить на карточке самого общего
  ресурса/формата, если ни одна из двух реальных сторон не выделена как главная. Это ДЕФОЛТ, не
  железное правило.
- Обратный вид («кто читает МЕНЯ») граф ВЫЧИСЛЯЕТ и показывает при рендере той цели — не
  дублируется руками на карточке цели.

## Поведение штампа

**Если секция уже есть — штамп её НЕ ТРОГАЕТ вообще**, кроме строки-контракта (она перезаписывается
как факт). Тул не может восстановить рантайм-связь из источника — значит вся таблица целиком это
проза человека/агента, сохраняется бережно, как любая другая прозa при merge.

**Если секции нет — штамп МОЛЧА не проходит мимо, если увидел подозрительные паттерны.** Не сыпет
простыню и не пишет директиву заранее (пустая секция во всех карточках — тот же анти-паттерн, что
REQ-009). Вместо этого — одна короткая строка-намёк в обычном выводе штампа, и **вся подробность —
за отдельным флагом**, не в теле карточки.

**Флаги — переиспользуем существующую CLI-конвенцию тула, не изобретаем новую.**
`make_interface_card.py --help` подтвердил: файл уже адресуется позиционным аргументом/`--file`
(`make_interface_card.py <file> ...`) — значит НЕ нужен отдельный `--info-seams <file>` с
собственным файловым аргументом (дублирование). Правильно:
- **`--help-seams`** (без файла, как `--help`) — печатает полный контракт секции: колонки, словарь
  Kind/Shape, примеры. То, на что ссылается строка-контракт в карточке.
- **`<file> --info-seams`** (обычный булевый флаг поверх уже существующего `<file>`/`--file`) —
  печатает найденные по известным паттернам подозрительные строки ИМЕННО в этом файле (номер
  строки + что нашли), не решает Kind/Shape/Why сама — это задача агента. Сужает работу с
  «прочитай весь файл в поисках чего-то динамического» до «просмотри вот эти N строк и
  классифицируй».

Точные имена (`--help-seams`/`--info-seams`) — рабочие, не сверены на коллизию с будущими флагами,
но САМ ПРИНЦИП (переиспользовать `<file>`, не дублировать) теперь зафиксирован, не открытый вопрос.

**Сканер — отдельный, самостоятельный модуль (детектор), не логика внутри `make_interface_card.py`
напрямую.** Начинаем с простого списка паттернов, усложняем по мере находок — как `BLACKLIST_DIRS`/
`ESCALATE_*`, конфигурация, а не жёсткий код. Список ниже — НЕ полный, только затравка:
- by-path/process (Python): `spec_from_file_location`, `importlib.import_module(computed)`,
  `subprocess.run`/`Popen`, `os.system`. (JS): `import(computed)`, `require(computed)`,
  `child_process.spawn`/`exec`. (C#): `Assembly.Load`, `Process.Start`.
- http: `requests.get/post`, `fetch(...)`, `ctx.rest(...)`, `axios.*` — литерал роута часто
  вытаскивается прямо из вызова.
- event: `.on(...)`, `.emit(...)`, `subscribe/publish` — имя события тоже часто литерал.
- `file` — сознательно НЕ включаем в сканер: `open(path)` встречается на каждом шагу и почти
  всегда НЕ рантайм-шов (обычное чтение конфига), слишком много ложных срабатываний.

## TLDR

`make_interface_card__TLDR.md` должен упомянуть `--help-seams` одной строкой — иначе флаг
существует, но никто не узнает, что его стоит искать.

## Потребитель — `graph_from_cards.py`

Читает эту таблицу со ВСЕХ карточек, рисует рёбра ОТДЕЛЬНЫМ видом (не смешивая с импортами) —
например пунктиром, с подписью `kind — shape`. Обсуждали мермейд как формат ХРАНЕНИЯ — отклонено
(проблемы парсинга компаунд-меток, сшивка id между карточками); как формат ГЕНЕРАЦИИ мермейд не
обязателен — важен сам факт, что швы должны БЫТЬ УЧТЕНЫ в существующих текстовых видах
(`--view depth`/`--view tree`), не то, в каком именно рендере. Ключевое: заметка «the map has N
independent parts» (уже существующая в `--discrepancies`) должна учитывать рантайм-швы — острова,
соединённые швами, уже не острова, и это самое важное следствие всей секции для графа.

## Заодно — переименование (тот же version-бамп, чтобы не плодить отдельную breaking-волну)

`Dependencies Internal` → **`In-Project Dependencies`**, `Dependencies External` → **`External
Dependencies`** — старые названия путают («Internal» читается как «внутри файла», а не «внутри
проекта»). Решили делать вместе с Runtime Seams, не отдельным поводом — три уже задеплоенных
проекта (`ProjectStarter`, `memohood`, `hermes-filetools`) иначе получат два breaking-события формата
подряд вместо одного.

## Валидатор (`validate_cards.py`) — что должен проверять

- `Kind` ∈ {by-path, process, http, file[:reads|:writes|:reads+writes], event[:emits|:listens]} —
  закрытый список, опечатка/самодеятельность = issue.
- `Shape` ∈ {dependent, equal, reference} — закрытый список.
- `Target`, если резолвится в путь ПРОЕКТА — та же логика `pending`/`unresolved`, что уже есть у
  `Dependencies Internal` (исходник есть, карточки нет = pending, не ошибка; ни исходника, ни
  карточки = ошибка). Если Target — свободный текст вне проекта (внешний бинарник, шина, URL) —
  не резолвится, не ошибка, просто заметка без ребра.

## Решено по ходу ревью (было открытым вопросом, теперь зафиксировано)

- **Флаги не дублируют существующий `<file>`.** `--help` подтвердил: файл уже адресуется
  позиционным аргументом/`--file`. `--info-seams` — обычный булевый флаг поверх него
  (`<file> --info-seams`), не отдельная сущность со своим файловым параметром. `--help-seams` —
  без файла, как штатный `--help`. Точные имена всё ещё не сверены на коллизию с другими будущими
  флагами, но принцип (переиспользовать, не дублировать CLI-конвенцию) зафиксирован.
- **Сканер — отдельный модуль-детектор**, не логика внутри `make_interface_card.py`. Список
  паттернов начерно намечен выше, заведомо не исчерпывающий — расширяется по находкам, как
  `BLACKLIST_DIRS`/`ESCALATE_*` (конфигурация, не жёсткий код). Простое начало, сложность — потом.
- **Hint при `--all`** — просто список имён файлов в обычном выводе: «suspected dynamic
  connections (grep detector) in: a.py, b.js — see `<file> --info-seams` for detail». Без счётчиков
  и отдельной сводки, тот же стиль, что уже есть у `--all`'s `NEW/merged/blocked` строки.
- **Мермейд-схема, собранная из таблиц швов со всех карточек** — это и есть предполагаемый новый
  вид `graph_from_cards.py` (условно `--view seams-mermaid` или флаг к существующим видам; точное
  имя/сигнатура — деталь реализации, не открытый вопрос по сути). Данные уже табличные и чистые
  (Target/Symbol/Kind/Shape) — сборка одной цельной диаграммы проекта из них дешёвая, без проблем
  сшивки id, которые были у идеи хранить мермейд в самой карточке (см. выше). Плюс это же должно
  быть учтено в заметке «N independent parts» у `--discrepancies` — острова, соединённые швами, уже
  не острова.
- **Миграция 8 живых `RUNTIME SEAM`-карточек — ПОСЛЕ кода**, как часть проверки реализации на
  реальных данных (тот же подход, что был с `memohood`/`hermes-filetools` в Plan02) — не отдельная
  подготовительная работа, не блокирует написание плана.

## Открытые вопросы (честно нерешено, не план — только зафиксированы)

1. Полный список паттернов-кандидатов для детектора — только затравка, реальный список выяснится
   по ходу работы с ним на живых проектах.
2. Механика парсинга «секция есть — не трогать целиком, кроме строки-контракта»: это частичный
   merge ВНУТРИ одной секции (обычно секция либо вся факт, либо вся проза; здесь смешанная — одна
   факт-строка сверху + вся остальная проза/таблица снизу) — нужно продумать в момент реализации,
   не проработано здесь.
