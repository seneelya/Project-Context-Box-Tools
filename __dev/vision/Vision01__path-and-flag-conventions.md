## 1. Проблема (не гипотеза — измерено)

Живой кейс из REQ-002: cwd = `<project>/__HQ/tools/`, `PROJECT_ROOT` = корень проекта (на два
уровня выше). Человек/агент сидит в `__HQ/tools/` и пишет путь ОТНОСИТЕЛЬНО СЕБЯ:

```
find_code_usage.py --file ../../file_ops/_new_format.py
```

Тул клеит этот путь к `PROJECT_ROOT`, а не к тому месту, где реально стоит вызывающий — путь
уезжает мимо, и опасность не в неудобстве, а в том, что склейка может СЛУЧАЙНО попасть в
СУЩЕСТВУЮЩИЙ файл (тихая неверная адресация, не крэш).

### Аудит по факту (не по памяти), снят 2026-08-29

**Флаг адресации цели:**

| `--file` (флаг) | позиционный аргумент |
|---|---|
| `find_code_usage.py`, `get_codeblock.py`, `graph_from_cards.py` | `make_interface_card.py`, `show_pyfile_api.py`, `collect_card_bundle.py` (`target`), `replace_in_files.py` (`PATH`+`MASK`) |

**От чего резолвится ОТНОСИТЕЛЬНЫЙ путь адресации:**

| от cwd (совпадает с ожиданием человека) | от `--project-root` (баг) |
|---|---|
| `get_codeblock.py`, `show_pyfile_api.py` | `find_code_usage.py`, `make_interface_card.py` |

**Каскад `--project-root` (флаг > `CONFIG__TOOLS.PROJECT_ROOT` > cwd) — есть не везде:**

| есть каскад | нет / свой баг |
|---|---|
| `validate_cards.py`, `graph_from_cards.py`, `get_codeblock.py` | `make_interface_card.py` (default=".", конфиг не спрашивает вообще); `collect_card_bundle.py` (флага `--project-root` нет вовсе); `check_cards_freshness.py` (корень выводит из `cards_dir.parent` — REQ-002-B, отдельный баг) |

**Стиль разбора аргументов — три разных механизма, патч не единая замена одной строкой:**

| чистый `argparse` | гибрид (argparse + ручной разбор) | полностью ручной `sys.argv` |
|---|---|---|
| `find_code_usage`, `make_interface_card`, `validate_cards`, `graph_from_cards`, `check_cards_freshness`, `collect_card_bundle` | `replace_in_files.py` | `get_codeblock.py`, `show_pyfile_api.py` |

`replace_in_files.py` — особый случай и по смыслу: не про «корень проекта» вообще, это
универсальная лопата (папку для работы можно указать где угодно), у неё уже есть свой алиас `@` →
`PATH == "@"` → `CONFIG__TOOLS.PROJECT_ROOT`, но БЕЗ защиты от отсутствия конфига (упадёт
трейсбеком).

## 2. Принцип: явность вместо магии, но не одинаковая для всех тулов

### Общий алиас `@`, без общего кода

`@` как значение флага — алиас на `CONFIG__TOOLS.PROJECT_ROOT`, единый по смыслу везде, где
встречается (`--project-root`, `--path`). Но **общего хелпера-модуля для резолва НЕ будет** —
осознанно: тулы намеренно держатся независимыми друг от друга (кроме прямых библиотечных
зависимостей вроде `make_interface_card` → `find_code_usage`/`get_codeblock`), и вводить новую
общую зависимость ради 3-5 строк логики — плата за унификацию больше, чем сама унификация стоит.
Каждый тул реализует резолв `@`/cwd/литерал у себя, дублируя маленький кусок кода. Сложность здесь
не в коде (он тривиален), а в идеологии — и в этом случае идеология против одного модуля.

### Два разных поведения по умолчанию — по категории тула, не единое

Ключевое уточнение сессии: «без флага = cwd» НЕ подходит одинаково всем. Причина — часть тулов
имеют структурно необходимое понятие корня (карточный слой `__map/` физически существует только
относительно корня проекта, не относительно того, откуда запущен тул), другие — нет.

**Generic-тулы** (`find_code_usage`, `get_codeblock`, `show_pyfile_api`, `replace_in_files`'ов
`--path`) — нет постоянного места на диске, привязанного к корню; cwd как дефолт осмыслен:

- флаг не задан → база = cwd;
- флаг = `@` → база = `CONFIG__TOOLS.PROJECT_ROOT`, явно, по запросу;
- флаг = литеральный путь → база = этот путь буквально.

Конфиг здесь не читается НИКОГДА молча — только по явному `@`. Это тот самый принцип «без флага
нет неявной работы», и здесь он держится без исключений.

**Card-тулы** (`make_interface_card`, `validate_cards`, `check_cards_freshness`, `graph_from_cards`,
`collect_card_bundle`) — `__map/` не существует «относительно cwd» в принципе: если запустить из
`__HQ/tools/`, карточка уедет туда, а не в реальный корень. cwd-дефолт тут не «может быть неверным»,
он **бессмысленен структурно**. Поэтому для этой категории — осознанное и единственное исключение
из «без флага нет неявной работы»:

- флаг не задан → база = `CONFIG__TOOLS.PROJECT_ROOT`, **неявно**, НО с проверкой на вменяемость
  (см. ниже) — без неё card-тулы требовали бы `--project-root` на каждый вызов, что для основного
  сценария работы (агент стоит в корне проекта, конфиг уже настроен деплоем) невыносимо;
- флаг = `@` → база = `CONFIG__TOOLS.PROJECT_ROOT`, явно — **без проверки**: пользователь осознанно
  так решил, значит имеет право получить что угодно, даже подозрительное;
- флаг = литеральный путь → база = этот путь буквально, **без проверки**.

**Проверка на вменяемость** (только для неявного случая — флаг не задан вообще): резолвленный
корень обязан быть ПРЕДКОМ папки, где физически лежит сам тул (`os.path.dirname(os.path.abspath(__file__))`
— для развёрнутого тула это `<root>/__HQ/tools`). Если нет — отказ с понятным сообщением
(«`CONFIG__TOOLS.PROJECT_ROOT` не похож на корень ЭТОГО проекта — передай `--project-root` явно»),
а не тихая работа не пойми над чем. Это и есть подстраховка от ровно того, что нашла REQ-002-C
(протухший/чужой конфиг), но не ценой неявной работы вообще — только ценой явного отказа, когда
неявное предположение выглядит подозрительно.

Никакого отказа «файл вне корня» отдельно вводить не нужно — если всё резолвится валидно, этого
достаточно, лишняя проверка не добавляет пользы.

### Почему не переименовать `--project-root`

Рассматривали `--home`/`--home-root` (отклонено — конфликтует с общепринятым смыслом `$HOME`/
`--home` в CLI-мире как домашней директории ОС/приложения, а не проекта) и общее `--path` для
всех тулов сразу (отклонено — стирает разницу между «весь корень проекта» и «произвольная папка
адресации», важную именно для читаемости слабой локальной моделью). Итог: **не переименовываем**,
`--project-root` остаётся; `replace_in_files.py` получает СВОЙ `--path` (у него нет понятия
«проект» вообще), с тем же алгоритмом резолва, но по generic-правилам (никогда неявно).

### Почему `--file` — унифицируемый флаг, а не позиционный

Большинство тулов (`find_code_usage`, `get_codeblock`, `graph_from_cards`) уже используют
`--file` — это и стало целевым именем. Позиционные `make_interface_card.py <file>` и
`show_pyfile_api.py <file>` получают `--file` КАК АЛИАС (позиционный аргумент остаётся рабочим,
не ломаем существующие вызовы/скрипты/доки). `collect_card_bundle.py`'s `target` и
`replace_in_files.py`'s `PATH`/`MASK` — тоже получают именованные флаги тем же способом.

### Порядок флагов в записи — уже задокументирован, распространяем на весь пакет

`Vision03__get_codeblock.md` («Грамматика вызова: команда = предложение», зафиксировано
2026-08-19) уже даёт канонический порядок для `get_codeblock`:
```
--project-root R  --file F  --line N  (--level N | --ancestor-level N)  (--outline|--query|--dot)  --numbered  --force
```
Роли: **ГДЕ** (адрес, сужаем слева-направо: `--project-root` → `--file` → `--line` → уровень) →
**ЧТО** (глагол-действие) → **КАК** (наречия-модификаторы в хвосте, `--force` — последнее слово).
Флаги позиционно-независимы для парсера — порядок это соглашение ЗАПИСИ (доки/примеры/`--help`),
не требование парсера. Распространяем этот же принцип на весь пакет: везде пишем
`--project-root`/`--path` первым, затем `--file`/`--mask` (адрес), затем глагол-флаги
(`--force`/`--out`/`--view`/…), затем модификаторы в хвосте.
`test/human_test_commands_make_interface_card.txt` (и подобные) сейчас пишут позиционный файл
ПЕРЕД `--project-root` — не приоритет чинить (эти файлы переписываются легко и часто), но при
следующей правке привести к канону.

## 3. Как чинится сама REQ-002-C (сид конфига) — через деплой, не только нейтральный шаблон

Просто «сделать сид пустым» — полумера. Настоящее решение: **`deploy_hq.py --init` сам вычисляет
реальный абсолютный путь `--target` и ЗАПИСЫВАЕТ его строкой в `CONFIG__TOOLS.PROJECT_ROOT`**
свежесеянного конфига — вместо статичного списка кандидатов «повезёт/не повезёт». Тогда конфиг
каждого развёрнутого проекта гарантированно правильный ДЛЯ СЕБЯ, не угадывание по существованию
пути на диске — и именно это делает неявное чтение конфига в card-тулах (§2) безопасным.

Локальная копия `CONFIG__TOOLS.py` здесь, в самом репозитории `tools` (используется для разработки
и тестирования тулов против memohood) — вне этого механизма (никогда не была «развёрнута», это
исходный сид сам по себе). Она остаётся НЕЙТРАЛЬНОЙ/пустой — репозиторий уходит другим людям на
тест, у них пути другие. Для локальной разработки/тестов, где нужны реальные данные — явный
фикстур-путь + при необходимости monkeypatch конфига, НЕ общий сид. `test/test_cardstamp.py` уже
так делает (`_PR = os.path.join(_HERE, "pythonSRC")`, `CONFIG__TOOLS` не читает вообще) — менять
не нужно, уже соответствует.

## 5. Что НЕ делаем

- Не переименовываем `--project-root` (см. §2).
- Не убираем позиционные аргументы там, где они уже есть — только добавляем `--file`/`--path`
  как алиасы.
- Не заставляем `--path` замещать `--project-root` где-либо, кроме `replace_in_files.py`.
- Не вводим общий модуль-хелпер резолва — дублируем маленькую логику в каждом туле осознанно.
- Не добавляем отказ «файл вне корня» — если резолв валиден, этого достаточно.
- Не трогаем `get_codeblock.py`, кроме добавления `@`-алиаса.
