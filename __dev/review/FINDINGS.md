# Подтверждённые дефекты get_codeblock

Ревью от 18 октября 2026 года, ревизия `cb03914`, ядро `0.8.0`. P2 означает функциональную ошибку, которую стоит исправить; P3 — менее значимую проблему обработки ввода. Каждая запись ниже подтверждена запуском на временном файле. Исходники проекта не изменялись.

Примеры использует [probe_cases.py](probe_cases.py); полный результат находится в [validation/probes.json](validation/probes.json). Команды ниже подразумевают запуск `get_codeblock.py` из корня tools системным Python с установленными грамматиками. `--force` отключает расширение контекста, чтобы показать именно выбранный блок.

## R01 Многострочный декоратор исчезает из извлечённой функции

**P2.** Место: [python_handler.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/handlers/python_handler.py:532), `collect_preamble`, строки 532–543.

```python
@decorator(
    option=True,
)
def target():
    return 42
```

Для `--line 4 --level 1 --query --force` возвращаются строки **4–5**. Карта этого же файла показывает определение **1–5**. При запросе строки 1 декоратор попадает в результат, то есть диапазон одного определения зависит от точки входа.

Обратный проход `collect_preamble` останавливается на `)`: он умеет приклеивать только строки, начинающиеся с `@` или `#`. В комментарии к реализации ограничение прямо названо допустимым, но контракт ридера, инвариант 6, требует совпадения диапазонов и включения декораторов в преамбулу. Ограничение также отсутствует среди пользовательских оговорок TLDR.

Результат представляет функцию без её декоратора. Это меняет смысл контекста; `split_monster.cut`, использующий тот же API, получает такой же неполный диапазон. Фактический разрез такого файла в рамках этого воспроизведения не выполнялся.

Исправление должно находить начало всего выражения декоратора, включая продолжения строк. Критерий: запрос по `@`, закрывающей скобке, `def` и телу при выборе уровня определения согласуется с картой и содержит весь декоратор. Проверить также несколько декораторов и декорированные классы.

Ключ результата: `multiline_decorator`.

## R02 Повторное использование Source смешивает две версии файла

**P2.** Места: [views.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/views.py:433), [reader.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/reader/reader.py:70), [classify.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/reader/classify.py:428).

Сначала `views.open_source(path)` открывает двухстрочный файл:

```python
def old():
    return 1
```

После этого файл на диске заменяется четырёхстрочной версией с комментарием, пустой строкой и `def new()`. Вызов `query_view(src, [1], [0], force=True)` на сохранённом `src` возвращает диапазон **1–4** и подпись `def new():`. Однако рендер берёт текст из старого `src.lines`:

```text
#File: ...snapshot.py (2 lines)
#■BLOCK : 1-4
def old():
    return 1
#■END : 4
```

В `Source` хранится прежний текст, а адресация и карта заново читают `path`. Файл может измениться между обращениями в редакторе или при повторном использовании API. Получаются успешный ответ без ошибки и неверное утверждение о напечатанном диапазоне. Это нарушает точность framing даже при `--force`.

Нужна одна согласованная версия текста для карты, адресации и рендера: снимок в `Source` либо явное обнаружение изменения с согласованным обновлением или отказом. Простое обрезание `end` по старому размеру не исправит выбор другого блока.

Критерий: после замены файла все данные ответа относятся к одной версии; старый текст с новыми диапазонами недопустим.

Ключ результата: `snapshot`.

## R03 Unicode разделитель внутри строки сдвигает Markdown координаты

**P2.** Место: [markdown.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/reader/backends/markdown.py:69).

Воспроизведение создаёт файл с четырьмя физическими строками. Во второй строке находится символ `U+2028`:

```python
text = "# First\ntext\u2028continued\n## Second\nbody\n"
```

`core.read_lines` получает четыре строки. Markdown backend использует `str.splitlines`, который дополнительно разделяет строку по `U+2028`, и строит дерево из пяти строк. В карте `Second` находится на строке **4** вместо **3**, а диапазон `First` заканчивается на несуществующей строке **5**.

Запрос настоящей строки 3, `## Second`, возвращает диапазон **2–3** и текст `text\u2028continued\n## Second\n`, относящийся к неверно выбранной полосе. Это ошибка координат, а не только отображения Unicode.

Одинаковый способ разбиения применяется также в `plaintext.py:166`, `batch.py:111` и `python_ast.py:64`; динамическое воспроизведение здесь выполнено для Markdown. Следует определить общий способ физического разбиения строк и использовать его во всех потребителях, сохранив согласованную обработку LF, CRLF и CR.

Критерий: допустимые Unicode-символы внутри строки не меняют нумерацию относительно `read_lines`; каждый `end` находится внутри файла, запрос заголовка соответствует его реальному разделу.

Ключ результата: `unicode_lines`.

## R04 Короткая ограда закрывает более длинный Markdown fence

**P2.** Место: [markdown_handler.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/handlers/markdown_handler.py:38), строки 38–45.

Исходный документ, где внешний fence состоит из четырёх обратных кавычек:

`````text
# Real
````markdown
```
# Fake inside code
````
## Actual
body
`````

Ожидаемые заголовки — `Real` и `Actual`. Фактически карта показывает `Real [1–3]` и **`Fake inside code [4–7]`**, а настоящий `Actual` исчезает.

При открытии ограды код сохраняет только первые три символа маркера. Поэтому строка из трёх кавычек закрывает ограду из четырёх; настоящий закрывающий маркер затем принимается за новый открывающий. Такой документ обычен при показе примеров Markdown внутри Markdown.

Нужно сохранять тип и полную длину открывающей ограды и проверять допустимую закрывающую строку: тот же маркер, длина не меньше исходной, без содержимого после него кроме разрешённых пробелов.

Критерий: вложенные примеры с оградами разной длины не создают заголовков из кода; отдельно проверить тильды и строку, похожую на закрытие, но содержащую текст.

Ключ результата: `long_fence`.

## R05 Квалифицированный glob игнорирует ограничение класса

**P2.** Место: [name_resolver.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/name_resolver.py:227), строки 227–229.

В файле объявлены `A.foo` и `B.foo`. Точный запрос `A.foo` правильно находит только первый метод. Запрос **`A.foo*`** возвращает оба: `A.foo` на строке 2 и `B.foo` на строке 7.

Условие объединяет через `or` совпадение короткого имени с `foo*` и совпадение полного имени с `A.foo*`. Первой части достаточно для попадания любого класса. Большой набор посторонних совпадений может также занять лимит десяти кандидатов и вытеснить нужные результаты.

При наличии квалификатора нужно сопоставлять квалифицированный путь; проверку только короткого имени сохранять для неквалифицированного запроса. Следует сохранить или явно определить правила сопоставления суффикса пространства имён, которыми уже пользуется точный поиск.

Критерий: `A.foo*` исключает `B.foo`; аналогично работают `A::foo*` и шаблоны с `?`.

Ключ результата: `qualified_glob`.

## R06 Поиск имени теряет второе объявление одной инструкции

**P2.** Место: [name_resolver.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/name_resolver.py:192), строки 192–193; обход полей в `decl_name`, строки 105–117.

```typescript
export const FIRST = 1, SECOND = 2;
```

`declarations(path)` возвращает только `FIRST`. Запрос `--name SECOND --force` завершается с кодом **2** и сообщением `nothing similar`, хотя имя буквально объявлено в файле.

Для filler-узла вызывается один `add(ch, parents)`, а `decl_name` выбирает первый подходящий дочерний declarator. Остальные декларации инструкции не обходятся. Та же модель потенциально затрагивает другие языки с несколькими declarator в одном узле; подтверждённый пример — TypeScript.

Нужно собирать все объявляемые имена инструкции, сохраняя исключение импортов и локальных переменных. Дедупликация кандидатов по строке может остаться на уровне итоговой выдачи, но она не должна удалять имя до сопоставления запроса.

Критерий: оба имени находятся точным запросом; `SECOND` возвращает исходную инструкцию. Добавить отдельный пример с несколькими C/C++ declarator, если этот синтаксис входит в поддерживаемую поверхность.

Ключ результата: `multiple_declarations`.

## R07 Отображаемая подпись подменяет объявленное имя

**P2.** Место: [name_resolver.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/name_resolver.py:183), строки 183–186. Для AST backend: [python_ast.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/reader/backends/python_ast.py:46).

Подтверждены два проявления одного fallback в `declarations`:

1. В Markdown заголовок `# Getting started` при запросе `--name "Getting started" --force` считается **`no exact; closest 1 (words)`**, поэтому возвращается карта вместо тела раздела. Запрос нормализуется в `Gettingstarted`, а сохранённая подпись остаётся `Getting started`.
2. В Python без `tree_sitter_python` функция `def target(): ...` при запросе `--name target --force` считается **`no exact; closest 1 (substring)`**. `AstNode.field` всегда возвращает `None`, поэтому вместо `target` в записи оказывается отображаемая сигнатура `def target()`.

Оба вызова завершаются с кодом 0, но не исполняют документированное поведение для одного точного совпадения. Второй случай проверен отдельным Python 3.12 без грамматик; из системного Python зависимости не удалялись.

Ридеру нужен явный способ отдавать объявленное имя отдельно от подписи карты. Сопоставляемые имена и запросы должны проходить одинаковую нормализацию; использовать display label как готовое машинное имя недостаточно.

Критерий: оба примера дают точное совпадение и тело. Проверить также константу в AST fallback и квалифицированный метод класса.

Ключи результата: `markdown_heading_name`, `fallback_name`.

## R08 Импортируемый API меняет переводы строк

**P2.** Место: [core.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/core.py:308), строки 308–310.

Для файла с байтами:

```python
b"def target():\r\n    return 1\r\n"
```

`get_codeblock(path, 1, query=True)["text"]` возвращает:

```python
"def target():\n    return 1\n"
```

Открытие текстового файла без `newline` включает universal newline translation. Контракт API и TLDR обещают текст `byte-for-byte`, но CRLF теряется ещё до выделения блока. На уровне API это не зависит от того, как stdout конкретной платформы переводит символы при печати.

Потребитель, использующий результат для точной замены, сравнения или переноса текста, получает другую последовательность переводов строк. У `split_monster` есть собственное чтение исходных байтов и восстановление EOL; его прошедшие тесты не доказывают точность самого `get_codeblock`.

Следует сохранять исходные окончания строк при чтении и согласовать нумерацию с backend-ами. Если нормализация задумана как контракт, нужно явно изменить обещание и проверить потребителей; текущая реализация и документация противоречат друг другу.

Критерий: для LF, CRLF и смешанного файла текст диапазона совпадает с соответствующим исходным фрагментом, включая отсутствие завершающего перевода строки.

Ключ результата: `crlf`.

## R09 Ошибочные строки не отражаются в коде возврата survey и outline

**P2.** Места: [core.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/core.py:672), строки 672–675, и [core.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/core.py:714).

Для двухстрочного файла вызов `--line 1,999` печатает `ERROR: Line out of range`, но завершается с кодом **0**. С `--outline` результат такой же. Для тех же координат `--query --force` корректно возвращает код **1** и сохраняет полезный результат по строке 1.

В query ветке проверяется `view['errors']`. В batch outline ветка сразу возвращается после рендера. В survey ошибки присутствуют только в строках результата, а `_main_impl` их не проверяет. Автоматический потребитель, проверяющий exit code, принимает неполный или целиком ошибочный ответ за успех; журнал вызовов тоже фиксирует успех.

Нужно сохранить изоляцию ошибочного элемента и выдачу валидных результатов, но унифицировать ненулевой код возврата при ошибке координат во всех режимах. Для survey полезно вернуть отдельное поле `errors`, как у остальных views, чтобы CLI не разбирал строки рендера.

Критерий: смешанные и полностью ошибочные наборы дают ненулевой код в survey, outline и query; валидные элементы продолжают печататься.

Ключ результата: `invalid_lines`.

## R10 Пустой неизвестный аргумент вызывает traceback

**P3.** Место: [core.py](F:/WORK/ProjectStarter/__HQ/tools/get_codeblock/core.py:233).

Передача пустой строки как отдельного аргумента после `--file PATH` приводит к `IndexError: string index out of range`. Пустой элемент argv возможен, например, при вызове из скрипта с пустой переменной.

В ветке неизвестного аргумента условие подсказки обращается к `token[0]` без проверки длины. Ожидаемый результат — обычное сообщение `unrecognized argument` и ненулевой код, как для других неправильных токенов.

Достаточно безопасно проверять непустой токен перед индексированием. Критерий: `argv` с `""` завершается без traceback; числовая подсказка для неправильно переданного списка продолжает работать.

Ключ результата: `invalid_lines.empty_arg`.
